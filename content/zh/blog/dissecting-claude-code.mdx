Claude Code 是一个运行在 **Bun + Ink**（面向终端的 React）之上的 **TypeScript 单体应用**。仅 `main.tsx` 就超过 4,700 行，`REPL.tsx` 更是超过 5,000 行，并发出 288 次函数调用——是整个系统中扇出度最高的组件。

## 1. 架构：五层结构，一个引力中心

![架构概览](/images/blog/dissecting-claude-code/01-architecture.png)

CodeGraph 的分层发现揭示了一种**洋葱环式架构**，而 `src/utils` 正是它的引力中心。从上到下共有五层：

**入口层**——`REPL.tsx`（288 次调用、236 个导入）、`main.tsx`（275 次调用、163 个导入）和 `print.ts`（164 次调用，CLI 流水线）。它们是进入 Claude Code 的三扇门。

**UI 层**——共 131 个文件，其中包括拥有 113 个文件的 `components/` 目录、`PromptInput`（105 次向外调用）、Buddy 虚拟宠物系统，以及 Ink 的自定义终端渲染器（52 个方法）。

**逻辑层**——120 个 hooks、80 多条斜杠命令、42 个工具（从拥有 151 个函数的 BashTool 到只有 1 个函数的 SleepTool），以及 14 个快捷键绑定文件。

**服务层**——Analytics（428 个调用方）、MCP 协议（41 个文件）、Permissions（41 个文件）、Bridge 远程控制（33 个文件）、Swarm 多智能体系统，以及 7 种任务类型。

**基础层**——`utils/` 目录包含 299 个文件，承接了 **5,951 次传入调用**，是排名第二模块的 6 倍。它不是一个普通的工具目录，而是整个代码库的现实基岩。

### REPL：导入整个宇宙的组件

`REPL.tsx` 从 **236 个文件**导入内容，比代码库中的任何其他文件都多。它连接 hooks、components、services、bridge、swarm、voice、成本追踪、MCP 和快捷键绑定。然而，它的调用方数量却是 **0**（扇入度 = 0）。它是没人会调用的 UI 根叶节点，只向外发起调用。

## 2. 桥接函数：系统的神经中枢

![桥接函数](/images/blog/dissecting-claude-code/02-bridge-functions.png)

**桥接函数**是被最多不同模块调用的函数——它们是把不同子系统黏合在一起的连接件。CodeGraph 找出了以下顶级桥接函数：

| 函数 | 文件 | 跨越模块数 | 调用方总数 |
|------|------|-----------:|-----------:|
| `logForDebugging` | debug.ts | **90** | 911 |
| `logEvent` | analytics/index.ts | **94** | 428 |
| `logError` | log.ts | **77** | 413 |
| `set` | fileStateCache.ts | **64** | 290 |
| `jsonStringify` | slowOperations.ts | **63** | 248 |
| `isEnvTruthy` | envUtils.ts | **47** | 194 |
| `getGlobalConfig` | config.ts | **44** | 163 |
| `getCwd` | cwd.ts | **43** | 135 |

在 306 个模块中，有 **90 个模块**调用了 `logForDebugging`——几乎每 3 个模块中就有 1 个通过这个函数输送调试信息。它是 Claude Code 无所不见的眼睛。

值得注意的是，`jsonStringify`（248 个调用方、跨越 63 个模块）位于名为 `slowOperations.ts` 的文件中。团队特意把 JSON 操作封装进一个名为“slow”的模块——坦率地承认序列化是他们希望追踪的性能瓶颈。

仅排名前三的桥接函数，就贡献了跨越 **261 个模块边界**的 **1,752 条调用边**。移除其中任何一个，整个系统都会四分五裂。

## 3. 权限网关：唯一的咽喉要道

![权限网关](/images/blog/dissecting-claude-code/03-permission-gateway.png)

最具架构意义的发现之一是：**所有工具执行都会流经同一个函数**——`checkPermissionsAndCallTool`。它只有 **1 个调用方**（`streamedCheckPermissionsAndCallTool`），却会调用 **30 个不同的函数**，涵盖遥测、权限规则、分类器检查、错误处理和分析。

这是一个教科书式的**策略执行点（Policy Enforcement Point，PEP）**——所有 42 个工具在获得授权前都必须通过的单一关口。其下游函数包括：

- **checkRuleBasedPermissions**——评估规则引擎
- **startSpeculativeClassifierCheck**——“YOLO 模式”分类器
- **resolveHookPermissionDecision**——基于 hook 的覆盖决策
- **logEvent + logOTelEvent**——双重遥测（Analytics + OpenTelemetry）
- **startToolSpan / endToolSpan**——追踪边界
- **formatZodValidationError**——模式验证

凭借这种架构，系统无需修改任何单独的工具，就能轻松增加安全策略、审计日志和速率限制。

### 151:1 的复杂度差距

工具之间并非生而平等。BashTool 拥有 **151 个函数**，涉及命令解析、沙箱、权限验证、超时管理、输出捕获和跨平台兼容；SleepTool 则只有 **1 个函数**。在同一个统一接口下，复杂度跨度达到了 151:1。

| 工具 | 函数数 | 类别 |
|------|-------:|------|
| BashTool | **151** | Shell 执行 |
| PowerShellTool | **101** | Windows Shell |
| AgentTool | **91** | 多智能体编排 |
| LSPTool | 35 | 语言服务器 |
| FileEditTool | 31 | 文件操作 |
| GrepTool | 8 | 搜索 |
| SleepTool | 1 | 等待 |

## 4. Buddy 系统：藏在开发工具里的抽卡游戏

![Buddy 系统](/images/blog/dissecting-claude-code/04-buddy-system.png)

最令人愉悦的发现或许是：Claude Code 内置了一套完整的**虚拟宠物系统**，其中包含抽卡机制、ASCII 艺术动画和 RPG 属性。

### 伙伴如何生成

1. 使用 `hashString()` 和盐值（`friend-2026-401`）对**用户 ID 进行哈希**
2. 用哈希值为 **Mulberry32 PRNG 设定种子**
3. 通过**确定性抽取**生成物种、稀有度、眼睛、帽子和属性
4. **缓存结果**（Buddy 每 500ms 渲染一次，不能每一帧都重新抽取）

“骨骼”（物种、稀有度、属性）在**每次读取时都根据哈希重新生成**，绝不会持久化到磁盘。只有“灵魂”（用户选择的名字和性格）会被保存。这意味着：

- **防作弊**：用户无法修改配置来伪造 Legendary 稀有度
- **模式安全**：修改物种数组不会破坏已保存的伙伴
- **确定性**：同一用户永远拥有同一个伙伴

### 十六进制混淆技巧

全部 18 个物种名称都被编码为十六进制字符码，以绕过构建时字符串过滤器：

```typescript
const duck = String.fromCharCode(0x64, 0x75, 0x63, 0x6b)  // "duck"
```

其中一个物种名称与 `excluded-strings.txt` 中列出的内部模型代号冲突，因此团队统一编码了**所有**物种。

### 抽卡稀有度分布

| 稀有度 | 概率 |
|--------|------|
| 普通（Common） | 60% |
| 非凡（Uncommon） | 25% |
| 稀有（Rare） | 10% |
| 史诗（Epic） | 4% |
| 传说（Legendary） | **1%** |

每个伙伴拥有 **5 项 RPG 属性**：DEBUGGING、PATIENCE、CHAOS、WISDOM、SNARK。ASCII 精灵图高 5 行、宽 12 列，待机动画包含 2–3 帧。15 帧待机序列中的第 `-1` 帧会触发罕见的眨眼动画。

## 5. Dream Task：在你写代码时做梦的 AI

![Dream Task](/images/blog/dissecting-claude-code/05-dream-task.png)

Claude Code 拥有一套**后台记忆整合系统**，会在你工作时真正运行——AI 会“梦见”过去的会话，以改善自己的记忆。

### 四道关卡（成本由低到高）

做梦开始前，必须通过四道按计算成本排序的关卡：

1. **时间关卡**（成本：1 次 `stat()` 调用）——距离上一次做梦是否已过去 24 小时？
2. **扫描节流**（成本：内存时间戳检查）——距离上一次扫描是否已过去 10 分钟？
3. **会话关卡**（成本：`readdir`）——是否有 5 个以上的新会话需要整合？
4. **锁关卡**（成本：`flock`）——基于文件的互斥锁是否空闲？

这样的顺序确保**低成本的拒绝最先发生**。大多数 API 轮次只用一次 stat 调用，就会在第一道关卡退出。

### 做梦的四个阶段

关卡全部通过后，系统会派生一个受限子智能体，它只有**只读 Bash 权限**（仅限 `ls`、`grep`、`cat`、`head`、`tail`）：

1. **定位（Orient）**——对记忆目录执行 `ls`，了解当前状态
2. **收集（Gather）**——对近期会话记录执行 `grep`，寻找模式和可复用知识
3. **整合（Consolidate）**——用提炼后的知识写入或更新记忆文件
4. **修剪（Prune）**——确保记忆索引小于 25KB，单条内容少于 150 个字符

### 文件系统重试技巧

如果一次做梦在途中被终止，系统会调用 `rollbackConsolidationLock(priorMtime)`，**回拨锁文件的修改时间**。这样，下一轮 API 调用时就能再次通过时间关卡——这是一个直接构建在文件系统之上的重试机制。

## 6. Swarm：多智能体编排

![Swarm 系统](/images/blog/dissecting-claude-code/06-swarm-system.png)

这是架构上最具雄心的模块：一个用于生成并管理 AI 智能体团队的**三层后端抽象**。

### 后端检测优先级链

生成队友时，系统会探测运行环境：

| 优先级 | 后端 | 代码行数 | 检测方式 |
|--------|------|---------:|----------|
| P1 | **TmuxBackend** | 765 | `ORIGINAL_USER_TMUX` 环境变量 |
| P2 | **ITermBackend** | 370 | `TERM_PROGRAM` + `it2 session list` |
| P3 | **InProcessBackend** | 340 | 始终可用（兜底） |

**PaneBackendExecutor** 适配器把 tmux/iTerm2 封装进 **TeammateExecutor** 接口，InProcessBackend 则直接实现同一接口。因此系统可以平滑降级：tmux → iTerm2 → 进程内运行。

### 为什么使用 AsyncLocalStorage？

当智能体被转入后台（Ctrl+B）时，多个智能体会在**同一个 Node.js 进程中并发运行**。AppState 是一个共享的可变对象。如果智能体 A 的遥测读取它，拿到的可能是智能体 B 的上下文。

AsyncLocalStorage 隔离了每条异步执行链，为每个智能体提供独立的身份气泡，而不需要进行进程隔离。

### 任务 ID 设计

每个任务都有一个唯一 ID：**单字母前缀** + 8 个随机 base-36 字符：

- `b` = bash，`a` = agent，`r` = remote，`t` = teammate，`w` = workflow，`m` = monitor，`d` = dream

仅看 ID 字符串就能立即识别类型，同时拥有 36^8 ≈ 2.8 万亿种组合。

## 7. 成本追踪器：顺着资金流向追查

![成本追踪器](/images/blog/dissecting-claude-code/07-cost-tracker.png)

成本追踪系统支持 **7 档定价**，并能为 Opus 4.6 动态选择档位：

| 模型 | 输入/1M | 输出/1M |
|------|--------:|--------:|
| Haiku 3.5 | $0.80 | $4 |
| Sonnet | $3 | $15 |
| Opus 4.5 | $5 | $25 |
| Opus 4/4.1 | $15 | $75 |
| Opus 4.6（fast） | **$30** | **$150** |

`getOpus46CostTier(fastMode)` 会根据 `response_speed` 动态选择档位——fast 模式的价格是 2 倍。

### 账单访问关卡

显示逻辑体现了细致的产品思考：

- **订阅用户（Max/Pro）**：**隐藏**成本（采用固定费率，显示成本反而会造成困惑）
- **拥有管理员/账单角色的 API key 用户**：**显示**成本（他们按 token 付费）

这由 `hasConsoleBillingAccess()` 控制；该函数会检查 `DISABLE_COST_WARNINGS` 环境变量、订阅状态、身份验证 token，以及组织/工作区角色。

### 追踪哪些内容

- `totalCostUSD`——累计美元金额
- `totalAPIDuration`——等待 API 响应所花的时间
- `totalToolDuration`——执行工具所花的时间
- `linesAdded / linesRemoved`——代码变更量
- `modelUsage`——按模型拆分的 token 用量
- `fpsMetrics`——终端渲染性能

所有这些数据都会持久化到项目配置中，并通过 `restoreCostStateForSession()` 在会话重启后继续保留。

## 8. 最孤独的 1,265 个函数

CodeGraph 找到了 **1,265 个孤立函数**——既没有调用方，也不调用其他函数。在总计 9,848 个函数中，它们占 **12.8%**，处于完全孤立状态。

它们位于哪里？

| 文件 | 函数总数 | 孤立原因 |
|------|---------:|----------|
| `bootstrap/state.ts` | **212** | getter/setter 被动态调用 |
| `sessionStorage.ts` | **153** | 动态属性访问 |
| `yoga-layout/index.ts` | **134** | FFI 绑定层 |

仅 `bootstrap/state.ts` 就有 212 个函数，是整个代码库中函数最密集的文件。它是一个全局状态机，为从会话 ID 到模型字符串的各种数据提供 getter 和 setter。静态分析无法识别动态属性访问，因此这些函数看起来“孤立”，尽管它们在运行时被频繁使用。

## 10. 值得借鉴的模式

### 无需持久化的确定性生成

Buddy 系统每次都根据 `hash(userId)` 重新生成 `bones`，只有 `soul` 会持久化。这既消除了模式迁移的麻烦，也能防止通过修改配置文件作弊。

### 按成本排列关卡

Dream Task 依次检查：内存标志 → 对文件执行 stat → 列出目录 → 获取锁。每道关卡都比上一道更昂贵，因此低成本的拒绝会最先发生。

### 单字母任务 ID 前缀

`b`ash、`a`gent、`r`emote、`t`eammate、`w`orkflow、`m`onitor、`d`ream——仅从 ID 字符串就能立即识别类型。

### 坦诚的函数命名

`getFeatureValue_CACHED_MAY_BE_STALE`、`slowOperations.ts`、`writeFileSyncAndFlush_DEPRECATED`——这些名字迫使调用方理解相应的取舍。

### 用 AsyncLocalStorage 隔离并发身份

多个智能体共享同一进程时，不要用全局状态存储身份。使用 AsyncLocalStorage 为每条异步执行链提供自己的上下文。

### 单一权限网关

让全部 42 个工具都经过同一个函数。增加一项安全策略只需修改一个文件，而不是 42 个。

## 结论

Claude Code 不只是一款 AI 编程助手，它还是一个面向 AI 智能体的**微型操作系统**。通过 CodeGraph 的结构分析，我们发现了：

- 一个承接 **5,951 次传入调用**、充当基岩的 `utils` 基础层
- 一个让**全部 42 个工具通过同一网关**的权限系统
- 一只拥有**抽卡机制和防作弊架构**的虚拟宠物
- 一个会在空闲时**梦见自身记忆**的 AI
- 一个横跨 tmux、iTerm2 和进程内运行的**三层多智能体编排系统**
- **1,265 个孤立函数**（12.8%）在静默中独处

图从不说谎。每一个伟大产品的背后，都有一套讲述自身故事的架构——你只需要正确的工具来读懂它。
