> *原来，heartbeat 一直在悄悄吃掉你的 Token。*

---

## 背景

[OpenClaw](https://github.com/openclaw/openclaw) 已成为最热门的开源 AI 网关项目之一。它拥有 18,000 多次提交和一个快速壮大的社区，将 Telegram、Discord、Slack、MS Teams、Lark、Matrix 等消息平台连接到各种 LLM 提供商。对于许多构建 AI 聊天机器人和智能体的团队来说，OpenClaw 已成为首选方案。

但随着采用率上升，用户抱怨也越来越多，其中一个问题尤为突出：**Token 消耗远高于预期**。用户反馈 Token 预算莫名流失、对话历史无限增长，以及系统提示词膨胀到 29K 字符。即使配置了 `lightContext: true`，有些用户仍会反复触及 200K Token 上限。这些并非边缘案例，而是影响真实用户和实际预算的普遍痛点。

究竟发生了什么？是配置错误、模型问题，还是代码库本身存在更深层的原因？

为找出答案，我们使用 [NeuG](https://github.com/alibaba/neug)（图数据库）+ [zvec](https://github.com/alibaba/zvec)（向量索引）分析了整个 OpenClaw 代码库，生成了一张包含 **21,057 个函数和 35,761 条调用边**的代码知识图谱。结果令人意外：最大的 Token 消耗源之一就藏在眼前——**heartbeat 机制**。

本文将从最终用户的视角出发，追踪一个本应“轻量”的定时器如何变成吞噬 Token 的机器。后续文章还会从扩展开发者和核心维护者的视角继续分析。

---

## 问题：永不停止增长的会话历史

如果你正在使用 OpenClaw，并遇到以下任一情况：

- 对话历史无限增长，从不被截断
- 系统提示词意外膨胀（有用户反馈达到 29K 字符）
- 反复触及模型的 200K Token 上限
- 已在 HEARTBEAT.md 中配置 `lightContext: true`，却没有明显效果

这很可能不是配置错误或模型问题。一个很容易被忽视的原因是 OpenClaw 的 **heartbeat 机制**。

---

## Heartbeat 暗中做了什么？

OpenClaw 的 heartbeat 是一个周期性定时器。按设计，它本应是维持智能体存活的一次轻量 tick。我们使用 [CodeScope](https://github.com/codescope/codescope) 追踪了它的调用链，结果令人惊讶。

### 第一步：定位所有 heartbeat 相关代码

CodeScope 提供两种检索方式：文本搜索（字符串匹配）和语义搜索（向量相似度）。对于 OpenClaw 这样命名规范的代码库，关键词搜索通常足以定位核心代码。我们查询所有名称中包含 `heartbeat` 的函数：

```cypher
MATCH (f:Function)
WHERE f.name CONTAINS 'heartbeat' OR f.name CONTAINS 'Heartbeat'
RETURN f.name, f.file_path
ORDER BY f.file_path
```

查询返回了分布在 10 个模块中的 **68 个函数**，包括 infra、auto-reply、gateway、config、cron 等。我们使用 [neug-ui](/zh/docs/getting_started/neug_ui/) 将结果可视化：

![Heartbeat 函数分布](/images/blog/openclaw-token-cost-analysis/2026-03-18-openclaw-heartbeat-1.png)

infra 模块中的 heartbeat 相关代码最多，而且大部分集中在 `heartbeat-runner.ts` 中。

**传统方法通常到这里就停止了。** 找到这 68 个函数和核心文件后，常规的下一步是把代码交给 LLM，让它给出解释。这个过程本身会消耗 Token，而最终得到的是一段文字描述，并非可查询的结构。你无法直接追问：“谁调用了谁？”“调用链有多深？”“哪个函数是结构中心？”

图分析采用了不同的方法：**我们不读取代码内容，而是把函数之间的调用关系建模为图**，将结构性问题转化为图查询。

### 第二步：通过调用图找到核心入口

我们根据这 68 个函数之间的调用关系构建连通图，并按连通分量进行分组。最大的连通分量包含 **45 个函数**，说明它们组成了一个高度耦合的核心模块。其余 19 个连通分量平均只有 1.2 个函数，大多是独立的接口或配置函数。

随后，我们对最大连通分量进行了中心性分析：`runHeartbeatOnce` 在 **3 跳内连接了 27 个函数**，而排名第二的函数只连接了 6 个。差距十分明显：**`runHeartbeatOnce` 是整个 heartbeat 机制的核心入口**。结果如下：

![runHeartbeatOnce 中心性](/images/blog/openclaw-token-cost-analysis/2026-03-18-openclaw-heartbeat-2.png)

### 第三步：展开调用链——它究竟触达了什么？

我们展开 `runHeartbeatOnce` 的多跳出边，查找它直接或间接调用的所有上下文加载函数：

```cypher
// Find context-loading functions in the runHeartbeatOnce call chain
MATCH (f:Function {name: 'runHeartbeatOnce'})-[:CALLS*1..3]->(t:Function)
WHERE t.name CONTAINS 'Context'
   OR t.name CONTAINS 'Workspace'
   OR t.name CONTAINS 'Session'
   OR t.name CONTAINS 'Prompt'
RETURN t.name, t.file_path
ORDER BY t.file_path
```

结果如下：

![上下文加载函数](/images/blog/openclaw-token-cost-analysis/2026-03-18-openclaw-heartbeat-3.png)

**每一次 heartbeat tick 都会触发所有这些函数**——加载工作区目录、构建完整会话上下文、生成完整提示词。`runHeartbeatOnce` 有 **15 个直接被调用函数**，每一个都参与 heartbeat 配置解析和上下文组装。这正是 heartbeat 实际开销远超设计预期的结构性根因。

## 为什么 `lightContext: true` 没有帮助？

你可能已经在 HEARTBEAT.md 中设置了 `lightContext: true`，希望 heartbeat 只加载轻量上下文。

`lightContext` 是一个配置标志，但它无法改变调用链的结构。只要 heartbeat 的依赖树保持不变，每次 tick 就仍然必须加载工作区、构建会话上下文，并穿越多个模块。这条路径由代码结构决定，无法通过一个标志绕过。

我们还分析了最近 200 次提交的修改频率：负责上下文裁剪的 `context-pruning` 模块中，21 个函数有 4 个近期被反复修改。这表明 OpenClaw 团队已经意识到上下文膨胀问题，并在积极修复，但目前尚无稳定方案。

## 现在可以采取的四项实用缓解措施

**1. 将 heartbeat 视为重量级操作**

不要假设 heartbeat 是轻量的。估算 Token 预算时，应把每一次 heartbeat tick 都算作一次真实消耗事件。不要依赖 `lightContext: true` 来节省 Token。

**2. 降低 heartbeat 触发频率**

如果你的使用场景并不严格依赖实时 heartbeat 行为，降低触发频率是减少 Token 消耗最直接、最有效的方法。tick 越少，完整上下文加载次数就越少。

**3. 手动限制会话历史长度**

不要依赖 OpenClaw 自动截断对话历史。请在配置中明确设置最大历史记录数量，防止其无限累积。

**4. 监控周期性 Token 峰值**

在 LLM 提供商侧启用 Token 用量监控。如果你观察到周期性、时钟般规律的 Token 峰值，而不是随对话长度相关增长，那么很可能是 heartbeat 正在按计划触发完整上下文加载。

## 总结

我们从三个分析层面剖析了 heartbeat：

1. **函数分布**：68 个 heartbeat 相关函数分布在 10 多个模块中，最密集地集中在 `heartbeat-runner.ts`
2. **调用图中心性**：`runHeartbeatOnce` 是核心入口——有 15 个直接被调用函数，3 跳内可达 27 个函数
3. **调用链展开**：每次 tick 都会加载工作区目录并构建完整会话上下文，其负载与处理一条完整用户消息相当

这些发现共同解释了一个现象：**heartbeat 被设计成轻量定时器，但它的实际执行路径在结构上等同于一条完整的消息处理流水线。** `lightContext: true` 无法改变这一点。在官方修复推出之前，降低 heartbeat 触发频率并手动限制会话历史长度，是最有效的缓解措施。
