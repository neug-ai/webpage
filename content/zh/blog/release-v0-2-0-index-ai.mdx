如果你构建过 RAG 流水线或智能体记忆，很可能遇到过同样的瓶颈：语义搜索需要向量数据库，关键词搜索需要搜索引擎，关系推理需要图数据库。三个系统独立运行，数据同步、结果 JOIN 和扩展等问题全都压在了应用层。

这正是 NeuG v0.2.0 致力于解决的问题。本次发布的主题是：**为你的 Agent 应用打造全能数据索引** —— 统一的索引框架将 HNSW 向量搜索与 FTS 全文检索融为一体，并且两者都能在单条 Cypher 查询中与图遍历无缝结合。

以下是我们的构建初衷，以及它究竟带来了哪些核心特性。

---

## AI 工作负载对图数据库有哪些需求？

企业知识库问答、代码助手、智能体记忆——这些 AI 场景对底层数据库提出了三项检索需求：

- **向量搜索**：将文档和实体编码为向量，然后根据语义相似度检索最近邻。这是 RAG（检索增强生成）的核心。
- **全文搜索**：精确的关键词匹配，按 BM25 排序。这正是驱动用户搜索框的底层能力。
- **图遍历**：查找实体之间的关系路径，用于引用推理、影响分析和社区发现。

要同时满足这三项需求，通常只能选择以下两种现有方案之一，且各有取舍：

- **拼接多个系统。** 例如，Cognee 开箱即内置了三种存储——嵌入式图存储（Ladybug）、独立向量存储（LanceDB）以及 SQLite 数据库。虽然功能拼凑齐全，但代价是：数据在多个引擎间同步产生多份副本，需要运维多个系统，且检索结果需在应用层进行拼接。
- **让单一引擎同时支持这三项功能。** 例如，Graphiti 使用 Neo4j 作为后端，支持向量、全文和图检索。但问题在于，随着数据规模的增长，其检索性能会明显下降。

我们将在另一篇基准测试文章中详细对比和评估这些系统。

**v0.2.0 的核心在于将向量搜索和全文检索原生集成到图数据库中。** 无需数据搬运，无需额外系统——一条 Cypher 查询即可覆盖全部三种检索模式。

## 统一索引框架：向量与全文索引共用 CREATE INDEX

v0.2.0 引入了通用的 `StorageIndex` 框架——所有索引类型共享相同的生命周期（Init → Open → Rebind → BulkBuild，以及增量维护），并通过 Cypher DDL 进行管理。

这意味着创建不同类型的索引看起来几乎完全相同：

```cypher
-- Vector index (HNSW)
CREATE INDEX doc_vec_idx ON Document USING HNSW (embedding)
WITH (metric = 'cosine', m = 16, ef_construction = 200);

-- Full-text index (FTS)
CREATE INDEX doc_title_fts ON Document USING FTS (title);

-- List existing indexes
CALL SHOW_INDEXES() RETURN *;
```

该框架支持插件化：HNSW 由 `vector_search` 扩展提供，FTS 由 `fts` 扩展提供，未来的索引类型（B-tree、GIN 等）也以同样的方式作为扩展插入——无需修改内核。

## HNSW 向量搜索：图数据库的“语义雷达”

向量搜索已成为 AI 应用的必备基础功能。v0.2.0 版本通过 `vector_search` 扩展引入了 HNSW 近似最近邻索引。

### 基本用法

定义一个包含向量属性的节点表，然后构建索引：

```cypher
-- Node table: documents + a 768-dim embedding
CREATE NODE TABLE Document (
    id INT64,
    title STRING,
    embedding FLOAT[768],
    PRIMARY KEY (id)
);

-- Build an HNSW index (cosine distance)
CREATE INDEX doc_vec_idx ON Document
USING HNSW (embedding)
WITH (metric = 'cosine');
```

索引创建后，优化器会将普通的 `ORDER BY ... LIMIT K` 查询重写为 HNSW 索引扫描：

```cypher
-- Find the 10 documents most similar to the query vector
MATCH (d:Document)
RETURN d.id, d.title
ORDER BY vector_distance_cosine(d.embedding, $query_vec) ASC
LIMIT 10;
```

您只需编写标准的 Cypher 语句；优化器会识别向量距离函数 + ORDER BY + LIMIT 的组合，并自动使用该索引。

### 向量 + 图遍历

在找到相似文档后，继续遍历图以追踪引用关系——这是纯向量数据库无法做到的：

```cypher
-- Vector search first, then traverse the graph
MATCH (d:Document)
WITH d
ORDER BY vector_distance_cosine(d.embedding, $query_vec) ASC
LIMIT 10
MATCH (d)-[:CITES]->(ref:Document)
RETURN d.title, ref.title AS cited_doc;
```

## FTS 全文搜索：无需外部系统的关键词检索

向量搜索擅长处理语义相似度，但当用户搜索精确词汇、产品型号或带引号的短语时，他们需要的是关键词匹配。v0.2.0 版本中的 `fts` 扩展填补了这一空白——该扩展基于 SQLite FTS5 构建，并采用 BM25 算法进行排序。

### 基本用法

```cypher
-- Build a full-text index on the title property
CREATE INDEX doc_title_fts ON Document USING FTS (title);

-- BM25 Top-K search
MATCH (d:Document)
RETURN d.id, d.title,
       bm25(d.title, 'graph database') AS score
ORDER BY score ASC
LIMIT 10;
```

它支持丰富的查询语法：

| 搜索类型 | 示例 | 含义 |
|---------|---------|------|
| 词项 | `'database'` | 匹配包含该词项的文档 |
| 短语 | `'"graph database"'` | 匹配相邻的词项 |
| 前缀 | `'data*'` | 匹配以 `data` 开头的单词 |
| 布尔 | `'graph OR database'` | 匹配其中任意一个 |
| 排除 | `'graph NOT database'` | 匹配 `graph` 但不匹配 `database` |

### 全文搜索 + 图遍历

与向量搜索类似，全文搜索结果也可以继续进行图遍历：

```cypher
-- Full-text search first, then find citations
MATCH (d:Document)
WITH d, bm25(d.title, 'graph database') AS score
ORDER BY score ASC
LIMIT 10
MATCH (d)-[:CITES]->(ref:Document)
RETURN d.title, ref.title AS cited_doc, score;
```

## 混合搜索：向量 + 全文 + 图遍历，一条 Cypher

将这三种能力融为一体——这正是 v0.2.0 的核心要义。

假设你有一个知识图谱，其中的文档节点同时带有嵌入向量和基于标题的全文索引，并且节点之间通过 `CITES` 边相连。一个典型的检索查询如下所示：

```cypher
-- Step 1: vector search finds semantically similar documents
MATCH (d:Document)
WITH d
ORDER BY vector_distance_cosine(d.embedding, $query_vec) ASC
LIMIT 20

-- Step 2: full-text search reranks the candidates
WITH d, bm25(d.title, $keyword) AS text_score
ORDER BY text_score ASC
LIMIT 10

-- Step 3: traverse the graph to find citations
MATCH (d)-[:CITES]->(ref:Document)
RETURN d.title, ref.title AS cited_doc, text_score;
```

向量搜索负责粗过滤（筛选出语义最接近的 20 个文档），全文搜索负责重排（保留关键词最相关的 10 个文档），图遍历负责关系推理（这些文档引用了谁）。这三种检索能力在单条 Cypher 查询中无缝组合——无需跨系统结果 JOIN，无需应用层组装。

这就是“Agent 应用的全能数据索引”的真正含义——不仅仅是存储一个图，而是将 AI 所需的三种检索能力统一到一个引擎中，让它们能够自然地组合。

## 性能一览：实测数据

前面的章节介绍了索引查询语法；本节则提供了一组真实的基准测试结果。我们进行的是**自我对比**：相同的数据集、相同的查询，有索引与无索引的对比。后续文章将对 NeuG 与其他产品进行正面对比的基准测试。

**测试环境**：Apple M5 Pro 笔记本电脑（48 GB 内存），NeuG v0.2.0（PyPI 发布版），单进程嵌入式模式。数据为聚类的合成文档嵌入向量（384维，已归一化），接近真实嵌入向量的分布形态；查询使用未参与索引构建的留出向量，每个数据点均通过 21 次独立查询进行测量，并报告 p50 和 p95 百分位数结果。

### 向量搜索：HNSW 与暴力扫描对比

| 数据规模 | 暴力扫描 p50 | 暴力扫描 p95 | HNSW p50 | HNSW p95 | 加速比 p50 · p95 |
|---------|-----------|-----------|---------|---------|-----------------|
| 10k | 82.3 ms | 84.0 ms | 3.8 ms | 4.0 ms | ~22× · ~21× |
| 100k | 780.2 ms | 796.4 ms | 3.9 ms | 4.1 ms | ~202× · ~196× |

查询为 Top-10 余弦最近邻。在没有索引的情况下，系统会逐行计算距离，因此延迟随数据量线性增长；而 HNSW 仅访问极小比例的节点，因此无论数据规模如何，延迟基本保持不变——这就是为什么加速比随数据量增加而提升，在 10k 规模下约为 22 倍，在 100k 规模下约为 202 倍。

**召回率**：在两种规模下 recall@10 均为 1.0——HNSW 的 Top-10 结果与 float64 精确解以及 NeuG 暴力扫描结果逐项完全匹配，这意味着在真实形态的数据上，向量检索不会损失任何召回率；它没有用精度换取速度。需要注意的是，这些数据是**聚类**的（这正是真实嵌入向量的典型形态）；如果换成均匀随机向量，任何 HNSW 的召回率都会下降——这是数据形态问题，而非索引质量问题。

**一次性成本**：在 100k 行数据上构建 HNSW 索引（m=16, ef_construction=200）大约需要 78.6 秒。这是一次性开销；索引构建完成后，每次查询的延迟从近 1 秒降至 4 毫秒以下——对于读多写少的知识库工作负载，这种权衡绝对物超所值。

### 全文搜索：FTS 与 CONTAINS 扫描

| 数据规模 | CONTAINS p50 | CONTAINS p95 | FTS p50 | FTS p95 | 加速比 p50 · p95 |
|---------|-----------|-----------|--------|--------|-----------------|
| 10k | 20.9 ms | 21.4 ms | 0.25 ms | 0.50 ms | ~84× · ~43× |
| 100k | 205.9 ms | 216.7 ms | 2.47 ms | 2.73 ms | ~83× · ~80× |

查询为 Top-10 关键词检索。CONTAINS 对每一行进行子串匹配，因此延迟随数据规模线性增长；而 FTS 使用倒排索引，仅查找匹配项，因此几乎不受数据规模影响。此外，构建 FTS 索引仅需 0.01–0.07 秒——几乎零成本。

## 查询诊断：EXPLAIN / PROFILE

您编写了一个混合查询——如何知道哪个步骤是瓶颈？v0.2.0 新增了 `EXPLAIN` 和 `PROFILE` 模式：

```cypher
-- Show the query plan without running it
EXPLAIN MATCH (d:Document)
RETURN d ORDER BY vector_distance_cosine(d.embedding, $q) LIMIT 10;

-- Run it and collect operator-level metrics
PROFILE MATCH (d:Document)
RETURN d ORDER BY vector_distance_cosine(d.embedding, $q) LIMIT 10;
```

`PROFILE` 会打印一棵 ASCII 算子树，为每个算子标注其耗时和输出行数，该功能在 Python/Node.js/Java SDK 中均可使用。例如，在向量查询上运行 `PROFILE` 时，可以看到优化器将其重写为了 `IndexScanOpr`——也就是说，它使用了 HNSW 索引扫描，而不是暴力全表距离计算：

```
┌───────────────────────────────────────┐
│             IndexScanOpr              │
├───────────────────────────────────────┤
│   time: 0.04ms | rows:     3 tuples   │
└───────────────────────────────────────┘
┌───────────────────────────────────────┐
│         ProjectOrderByOprBeta         │
├───────────────────────────────────────┤
│   time: 0.01ms | rows:     3 tuples   │
└───────────────────────────────────────┘
┌───────────────────────────────────────┐
│              ProjectOpr               │
├───────────────────────────────────────┤
│   time: 0.00ms | rows:     3 tuples   │
└───────────────────────────────────────┘
┌───────────────────────────────────────┐
│                SinkOpr                │
├───────────────────────────────────────┤
│   time: 0.00ms | rows:     3 tuples   │
└───────────────────────────────────────┘
```

在编写复杂查询时，这是定位性能瓶颈的利器——哪个步骤慢、哪个步骤输出大量行，一目了然。

## 图管理：投影图命名空间

AI 应用通常跨越多个领域的知识子图——产品知识、用户行为、组织架构。v0.2.0 中的投影图命名空间允许您在单个数据库内定义命名空间隔离的图视图，从而使查询只能看到该视图内的节点和边：

```cypher
-- Define a namespace view: only database-category documents and their citations
CALL project_graph(
    'db_view',
    {'Document': "n.category = 'database'"},
    ['[Document, CITES, Document]']
);

-- Query within that namespace
USE NAMESPACE db_view
MATCH (d:Document)-[:CITES]->(ref:Document)
RETURN d.title, ref.title;

-- Clean up when done
CALL drop_projected_graph('db_view');
```

`project_graph` 使用节点/边谓词划分出一个子图，而 `USE NAMESPACE` 前缀将后续的 `MATCH` 语句限制在该视图内。不同的命名空间相互隔离，每个命名空间都有自己的过滤条件——无需按领域复制数据，也无需按领域建立单独的数据库。命名空间视图随检查点持久化，因此重新打开数据库后它们依然存在。

## 其他值得关注的改进

v0.2.0 还包含几项值得一提的改进：

- **显式事务**（[#938](https://github.com/alibaba/neug/pull/938)、[#944](https://github.com/alibaba/neug/pull/944)、[#950](https://github.com/alibaba/neug/pull/950)、[#951](https://github.com/alibaba/neug/pull/951)、[#967](https://github.com/alibaba/neug/pull/967)、[#899](https://github.com/alibaba/neug/pull/899)）：`begin_transaction() / commit() / rollback()` 现已支持 AP 和 TP 两种执行路径，并可在 Python / Node.js / Java 绑定中使用。
- **复杂数据类型**（[#507](https://github.com/alibaba/neug/pull/507)、[#726](https://github.com/alibaba/neug/pull/726)、[#829](https://github.com/alibaba/neug/pull/829)、[#871](https://github.com/alibaba/neug/pull/871)）：定长数组（`FLOAT[768]`）和变长列表（`LIST`）已实现端到端支持——涵盖存储持久化、WAL 以及 Parquet/CSV/JSON 导入。嵌入和标签可直接作为节点属性。
- **模式匹配扩展**（[#260](https://github.com/alibaba/neug/pull/260)）：子图匹配（使用 DAF 进行精确匹配 + 使用 FaSTest 进行采样匹配），适用于欺诈检测和生物网络分析。
- **树外扩展**（[#745](https://github.com/alibaba/neug/pull/745)）：第三方可构建自定义扩展，无需 fork 主仓库。
- **检查点重构**（[#678](https://github.com/alibaba/neug/pull/678)、[#892](https://github.com/alibaba/neug/pull/892)、[#904](https://github.com/alibaba/neug/pull/904)）：增量检查点仅写入脏数据；不可变对象加上原子 CURRENT 切换机制消除了部分写入导致的损坏，同时 GC 会回收旧检查点。
- **原生 Reader 框架**（`a281c0d`）：以自包含的读取框架取代 Arrow CSV/JSON IO。

完整发布说明请参见 [GitHub Release](https://github.com/alibaba/neug/releases/tag/v0.2.0)。

## 立即体验

```bash
pip install neug==0.2.0
```

```python
from neug import Database

db = Database("my_knowledge_graph")
conn = db.connect()

# Load extensions (run each statement separately)
conn.execute("INSTALL vector_search")
conn.execute("LOAD vector_search")
conn.execute("INSTALL fts")
conn.execute("LOAD fts")

# Create the table + indexes
conn.execute("""
    CREATE NODE TABLE Document (
        id INT64, title STRING, embedding FLOAT[768],
        PRIMARY KEY (id)
)
""")
conn.execute("CREATE INDEX doc_vec ON Document USING HNSW (embedding) WITH (metric = 'cosine')")
conn.execute("CREATE INDEX doc_fts ON Document USING FTS (title)")

# Import data, run hybrid search...
```
