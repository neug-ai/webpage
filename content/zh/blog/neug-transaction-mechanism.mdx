本文将深入介绍 NeuG 的事务机制。该机制在保证可串行化隔离的同时，为 NeuG 的高吞吐事务处理（TP）能力提供支撑。

**NeuG 仓库**：[https://github.com/alibaba/neug](https://github.com/alibaba/neug)

---

## 内容摘要

NeuG 是一款嵌入式图数据库，通过不同的执行模型同时支持事务处理（TP）与分析处理（AP）工作负载。

### 运行模式与并发

- **嵌入式模式**：分析查询以嵌入式模式运行，并在 Connection 级别管理并发。在一个给定的 AP Connection 中，所有查询（无论读写）均串行执行。该模型不使用本文针对 TP 所述的细粒度并行 MVCC 机制。

- **服务模式**：高吞吐 TP 操作通过内部服务层管理的单个 Write Connection 实现。该连接会创建多个并行执行的工作线程，借助本文介绍的 MVCC 与版本管理系统，实现无锁的读—插入并行以及可串行化隔离。

**范围**：本文详述支撑 TP 执行模型的事务机制。AP 模式则采用更简单的连接内串行方式来保证一致性。

---

## 核心架构与设计理念

事务设计的目标，是让常见图操作获得尽可能高的吞吐量。考虑到一种占主导地位的工作负载模式是高并发读取与盲插入混合运行，系统对事务进行分类，以消除不必要的同步。全局版本系统为读取者创建不可变快照；插入者则可以并行推进，仅在修改同一邻接表时才需要协调。

---

## 事务分类

NeuG 将事务分为三类，以优化并发执行：

| 类型 | 用途 | 关键特性 | 并发方式 |
|---|---|---|---|
| **Read** | 图遍历、点查询 | 纯读取；查看带版本的快照 | 通过 MVCC 与所有 Insert 并行 |
| **Insert** | 添加顶点/边 | 盲写；不读取已有图数据 | 与所有 Read 并行；对边的邻接表使用细粒度锁 |
| **Update** | 复杂 CRUD | 可见自身写入；支持中止/回滚 | 当前独占执行；未来采用两阶段设计 |

*重点：本文介绍 TP 工作线程池中 Read 与 Insert 事务的实现机制。*

---

## 版本管理：一致性的基础

NeuG 通过两个计数器维护一条全局单调递增的版本时间线：

- **全局写版本（Global Write Version，GWV）**：为写事务分配唯一 ID 的原子计数器
- **全局读版本（Global Read Version，GRV）**：能够保证此前所有写入均已提交的最高版本

### 事务版本分配

- **Read 事务**：启动时使用当前 GRV 作为其快照版本，且不会改变 GRV。
- **Insert 事务**：获取当前 GWV 作为其写版本，并以原子方式递增 GWV。

### GRV 推进逻辑

只有版本序列中连续的前缀全部完成后，GRV 才会推进。系统通过一个位集合在滑动窗口内跟踪完成状态。

![GRV 推进过程](/images/blog/neug-transaction-mechanism/2026-02-11-grv-advancement.png)

上图说明了 GRV 为何只有在连续的一段事务版本全部完成后才能推进。尽管在 STATE 1 中 v₄ 已经提交，但由于 v₁ 仍在等待，GRV 无法越过 v₀。v₁ 提交后，v₀–v₂ 形成连续的已完成序列，GRV 因而可以推进至 v₂。

## MVCC 存储与可见性

NeuG 实现了针对图工作负载优化的轻量级 MVCC 模型：

- **单版本模型**：每个顶点/边只存储一个 `write_version`（即其创建版本）
- **可见性规则**：版本为 `Tₓ` 的 Read 事务，当且仅当满足以下条件时才能看到某个元素：
  ```
  element.write_version ≤ Tₓ
  ```

这种单版本方式简化了存储与内存管理，同时为读取者提供快照隔离。

## 并发与隔离保证

### 读—插入并行

读取与插入之间能够实现无锁并行，原因如下：

1. **不存在读写冲突**：Insert 事务完全不会读取已有图数据
2. **非阻塞快照读取**：读取在不可变的版本快照上进行

### 写—写协调

- **顶点插入**：唯一性由调用方作为前置条件保证（假定顶点尚不存在）
- **边插入**：当并发事务向同一源顶点添加边时，按顶点设置的细粒度邻接锁可防止数据损坏。锁操作的原子性可以避免死锁。

### 可串行化隔离保证

- **读取**：单一版本快照天然可串行化
- **插入**：由 GWV 分配确定线性顺序，并通过 WAL 持久化（见下文）。由于不存在内部读取依赖，系统可以形成确定且可串行化的顺序。

## Insert 事务生命周期与持久性

Insert 事务遵循精心设计的协议，在兼顾性能的同时保证持久性：

```
1. 启动并分配版本
   └── 分配 GWV（例如 v₇）；以原子方式将 GWV 递增至 v₈

2. 预处理（只读阶段）
   └── 校验 ID 和 schema，编码属性
   └── 不修改图

3. 提交持久化（预写日志，WAL）
   └── 将所有变更数据刷入持久化 WAL
   └── 此处定义了持久性边界
   └── 中止时：记录一条最小化的中止标记

4. 原子应用
   └── 获取所需的顶点级邻接锁
   └── 以原子方式应用所有顶点/边插入，并标记版本 v₇
   └── 更新索引

5. 完成
   └── 在跟踪位集合中将事务 v₇ 标记为完成
   └── 在条件允许时推进 GRV（例如从 v₆ 推进至 v₇）
```

### 恢复

系统崩溃后，会恢复最近的检查点，并重放所有已提交的 WAL 记录以保证持久性。这一设计确保任何已提交事务都不会丢失，同时尽量缩短恢复时间。

## 性能特征

NeuG 的事务机制通过上述设计选择获得了多方面的性能收益：

### 高读取吞吐

- **零锁竞争**：Read 事务从不因锁而阻塞
- **无需遍历版本链**：单版本模型消除了多版本查找开销
- **快照隔离**：读取者无需协调即可看到一致视图

### 高效插入处理

- **并行执行**：多个 Insert 事务可同时执行
- **细粒度加锁**：只有共享同一源顶点的边才需要协调
- **最少同步**：无需处理读写冲突

### 可预测延迟

- **无锁读取**：查询延迟不受写工作负载影响
- **确定性版本分配**：所有事务都有明确顺序
- **基于 WAL 的持久性**：快速提交，并在后台持久化

## 设计权衡

### 优势

1. **针对读密集型工作负载优化**：并发读取这一常见场景没有额外开销
2. **实现简单**：单版本存储降低了复杂度
3. **强保证**：无需复杂协议即可实现可串行化隔离
4. **性能可预测**：无锁读取带来稳定延迟

### 当前限制

1. **Update 事务**：目前串行执行；未来将支持更高并发
2. **删除操作**：通过 Update 事务处理
3. **长事务**：可能暂时延迟 GRV 推进

## 实现细节

以下内容面向希望了解技术实现的开发者。

### 版本计数器设计

```python
class VersionManager:
    def __init__(self):
        self.gwv = AtomicCounter(0)  # Global Write Version
        self.grv = AtomicCounter(0)  # Global Read Version
        self.completion_bits = SlidingBitSet()
    
    def assign_write_version(self):
        return self.gwv.fetch_and_increment()
    
    def get_read_version(self):
        return self.grv.load()
    
    def mark_complete(self, version):
        self.completion_bits.set(version)
        self.try_advance_grv()
```

### 邻接锁协议

```python
class EdgeInserter:
    def insert_edge(self, src, dst, properties):
        # Acquire lock on source vertex's adjacency list
        with self.vertex_locks[src]:
            # Stamp with transaction version
            edge = Edge(src, dst, properties, self.tx_version)
            self.adjacency_lists[src].append(edge)
```

### WAL 格式

每条 WAL 记录包含：
- 事务 ID（版本）
- 操作类型（INSERT/UPDATE/ABORT）
- 载荷（带属性的顶点/边）
- 用于完整性校验的校验和

## 与其他方案的对比

### 与传统 RDBMS MVCC 对比

| 特性 | NeuG | 传统 RDBMS |
|---|---|---|
| 版本存储 | 每个元素一个版本 | 多版本链 |
| 读取开销 | 零锁竞争 | 可能需要遍历版本 |
| 写入模型 | 针对盲插入优化 | 通用更新 |
| 隔离级别 | 可串行化 | 通常为快照隔离 |

### 与图专用系统对比

| 特性 | NeuG | Neo4j | JanusGraph |
|---|---|---|---|
| 并发模型 | MVCC | 基于锁 | 乐观锁 |
| 读取并行 | 无锁 | 基于锁 | 无锁 |
| 事务范围 | 本地（嵌入式） | 本地 | 分布式 |
| 性能重点 | TP 工作负载 | 混合 OLTP | 面向 OLAP |

## 总结

NeuG 的事务机制通过以下方式，为图工作负载提供高吞吐、可串行化的隔离能力：

1. 将事务划分为 Read 与 Insert 类型
2. 通过 MVCC 与带版本快照实现隔离
3. 通过细粒度锁和全局版本顺序同步写入
4. 通过基于 WAL 的提交协议保证持久性

这一设计在嵌入式图数据库工作负载中实现了性能、简洁性与正确性的良好平衡。系统既能让无锁读取横向扩展，又能维持强一致性保证，因此非常适合同时要求高吞吐与事务完整性的现代 AI 和分析应用。
