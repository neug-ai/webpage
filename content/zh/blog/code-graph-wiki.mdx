由 LLM 生成的代码 Wiki，第一次看往往令人印象深刻。它能把分散的代码整理成易读的章节，并在很短时间内给出实用的解释。

但知识库并不是只生成一次就结束了。当我们再次对同一份代码执行这一流程时，LLM 并不会保留上一次的概念地图：章节可能被拆分或合并，同一段代码也可能被移到别处。例如，处理类型转换（`cast`）的代码，这次可能归在“类型系统”下，下次却可能出现在“内置函数”中。

代码本身发生变化时，第二个问题随之出现。LLM 必须根据 git diff 推断哪些 Wiki 章节需要更新。当影响跨越文件或目录边界时，它往往只更新最显眼的章节，却让其他受影响的章节停留在旧状态。

单独看，每次结果似乎都说得通。但放在一起，它们就不再像一个连贯的知识库：概念边界不断漂移，受影响的章节没有更新，几轮迭代之后，你很难再判断哪些内容仍然可信。

我们在维护 NeuG 的代码 Wiki 时遇到了这个问题。最终，我们把两项决策从 LLM 提示词中移出，交给图计算：构建 Wiki 时，根据代码关系推导概念边界；代码变化时，计算哪些概念受到影响。LLM 仍然负责阅读和写作；NeuG 则利用图来判断哪些文件应归为一组，以及发生了什么变化。

下文将以 NeuG 自身的代码库为例，说明这一流程如何运作。文末附有完整教程链接。

---

# LLM 能写 Wiki，但很难让它始终保持一致

**构建阶段：概念边界不稳定。** LLM 阅读代码后自行决定如何划分章节，但它往往沿用目录结构——而目录结构 ≠ 概念结构。`common/types/`、`function/cast/`、`function/comparison/` 都属于“类型系统”，LLM 却会把它们拆成两个互不相干的章节。

**更新阶段：影响范围不确定。** 代码发生变化后，LLM 阅读 git diff，猜测哪些 Wiki 章节受到影响。它经常只浏览几个章节便开始写作，真正发生变化的章节反而没有被触及。该更新的内容仍然陈旧，知识也随之逐渐腐化。

这两者首先都不是写作问题，而是关系问题：哪些文件属于同一个概念、一次代码变更影响了哪些概念，仅靠孤立地查看文件无法可靠判断。

我们用代码图为这些决策提供稳定依据。

# 构建：Leiden 划定边界，PageRank 选择文件

首先，我们把 NeuG 代码库构建成图：文件和函数作为节点，函数调用关系作为边。在符号级别，这张图约有 28,000 个节点和 52,501 条边。

但符号级别对于概念分组来说过于细碎，文件级别更合适。因此，我们把符号图聚合成文件级视图：“文件包含函数，函数彼此调用”被折叠为文件到文件的关系，最终得到 1,423 个文件节点和 3,869 条边。

这个视图只用于计算，因此我们使用 NeuG v0.1.3 的 COPY TEMP 将其导入为临时图——运行分析后丢弃临时数据，不会污染持久图。

接下来，我们在文件级图上完成两件事：

**第一，使用 Leiden 社区发现划定概念边界。** 关系紧密的文件会自然聚集到同一个社区中，不受目录结构限制。

```cypher
CALL leiden('code_graph', {concurrency: 1})
YIELD node, community
RETURN node.name, community
```

以 NeuG 代码库中的一个典型社区 **type-and-value-system** 为例。它包含 187 个文件，横跨 6 个路径前缀。下图用 6 个代表性元素比较了两种方法：图方法通过 Leiden 聚类，把类型、值、类型转换和比较正确归入同一个“类型系统”章节；LLM 方法则沿用目录结构，将其拆成 `common-types` 和 `built-in-functions`，切断了二者之间的语义联系。

![类型与值系统的聚类对比](/images/blog/code-graph-wiki/clustering_comparison.png)

**第二，使用 PageRank 为每个概念组挑选核心文件。** 社区确定之后，LLM 应该阅读哪些文件来撰写 Wiki？它通常会依赖启发式规则，例如选择文件名较短的文件。图方法则使用 PageRank 按全局引用次数对文件排序，直接找出最重要的文件：

```cypher
CALL page_rank('code_graph', {max_iterations: 20})
YIELD node, rank
WITH node, rank WHERE node.community = 37
RETURN node.name, rank
ORDER BY rank DESC LIMIT 5;
```

对于 `cypher-parser` 章节，PageRank 排名第一的是 `transformer.h`（330 行，声明了全部转换方法，被多个文件引用）；LLM 选择的却是 `use_database.h`（39 行，只有 1–2 处引用，仅仅因为文件名短且扩展名是 `.h`）。

PageRank 版本覆盖了 Transformer 类的 80 多种方法分派架构和运算符优先级链。LLM 选取文件后生成的版本虽然总体概述正确，却不得不推测核心架构，读者仍需自行查看源代码。差异不在写作风格，而在证据：一个版本阅读了真正支撑该章节的文件，另一个版本阅读的只是看起来相关的文件。

![PageRank 与 LLM 文件选择对比](/images/blog/code-graph-wiki/pagerank_vs_llm.png)

**第三，同样的分组可以重复得到。** 图计算每次都会产生相同输出，而 LLM 生成的 Wiki 每次都可能发生漂移：

![可复现性对比](/images/blog/code-graph-wiki/reproducibility.png)

# 更新：Leiden 分配新概念，Cypher 计算增量

构建阶段解决的是“第一次如何划分”。但代码每天都在变化——知识库不能划分一次后便置之不理。

NeuG 提供增量式 **freeze-assign Leiden 算法**：现有节点保留原来的概念归属，只有新增内容会重新聚类。一个之前属于“compiler”的模块，更新后仍属于“compiler”。概念不会漂移，差异也完全可比较。

```cypher
CALL leiden('code_graph', {concurrency: 1,
  initial_community_property: 'delta_comm'})
YIELD node, community, previous_community
RETURN node.id, community, previous_community;
```

**然后使用 Cypher 计算社区级增量**：按社区分组，精确衡量每个社区的变化——稳定 / 增长 / 新增。只有真正发生变化的社区才会交给 LLM；稳定的社区直接复用原内容。

```cypher
MATCH (n)
WITH n.community AS community, count(*) AS total,
     count(n.previous_community) AS old_members
RETURN community, total - old_members AS new_members,
  CASE WHEN old_members = 0 THEN 'new'
       WHEN old_members = total THEN 'stable'
       ELSE 'growth' END AS change_type;
```

LLM 方法：读取全部 35 个变更文件，逐一与 23 个章节比较。它可能标记 4 个章节需要更新，但其中两个是误报。

图方法：直接识别出 21 个概念（Wiki 章节）没有任何变化，另有 2 个概念增加了新成员——只有这两个章节需要增量更新。

# 在多次更新中维持同一个知识库

图并不负责撰写 Wiki。它回答的是两个需要长期保持一致的问题：哪些证据定义了一个概念边界，以及代码变化后哪些章节确实需要重写。

NeuG 根据代码关系计算边界和受影响范围。随后，LLM 阅读相关代码并撰写解释。目标不只是产出一个优秀的初始版本，更是让知识库经历多次更新后仍保持同一套概念结构，同时不遗漏已经变化的知识。

如果你也遇到过概念分组漂移，或在代码变更后难以判断该更新哪些章节，欢迎告诉我们你的项目中发生了什么。
