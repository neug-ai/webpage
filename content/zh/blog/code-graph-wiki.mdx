由 LLM 生成的代码 Wiki 在首次运行时往往令人印象深刻。它能将零散的代码转化为易于阅读的章节，并在极短的时间内生成有用的解释。

但知识库并非只生成一次。当我们对同一代码再次运行该流程时，LLM 并没有保留其之前的概念图谱：章节可能会被拆分或合并，相同的代码也可能被移至他处。例如，处理类型转换的代码（`cast`）在某次运行中可能出现在“类型系统”下，而在下一次运行中却跑到了“内置函数”下。

第二个问题出现在代码本身发生变更时。LLM 必须根据 git diff 推断哪些 Wiki 章节需要更新。当变更的影响跨越文件或目录边界时，它往往只更新最明显的章节，而将其他受影响的章节搁置，导致内容过时。

每次生成的结果单独来看似乎都挺合理。然而，将它们汇总在一起时，就不再像一个连贯统一的知识库了：概念边界发生漂移，受影响的章节未被触及，经过几次更新后，很难再分辨哪些内容依然可信。

我们在维护 NeuG 的代码 Wiki 时遇到了这个问题。最终，我们将两个决策从 LLM 提示词中移出，交由图计算来处理：在构建 Wiki 时从代码关系中推导概念边界，并在代码变更时计算哪些概念受到了影响。LLM 依然负责读写；而 NeuG 则利用图来决定哪些文件属于同一组以及具体发生了哪些变更。

本文的其余部分将展示这一机制在 NeuG 自身代码库中的运作方式。文末附有完整教程的链接。

# LLM 能写 Wiki，但保持连贯性却很难

**构建时：概念边界不稳定。** LLM 阅读代码并自行决定如何拆分章节。但它往往倾向于遵循目录结构——而目录结构 ≠ 概念结构。`common/types/`、`function/cast/`、`function/comparison/` 都属于“类型系统”，但 LLM 却将它们拆分成了两个独立的章节。

**更新时：影响范围不确定。** 代码发生变更，LLM 会读取 git diff 来猜测哪些 Wiki 章节会受到影响。它往往只扫过几个章节就开始动笔，而真正发生变化的章节却从未被触及。本该更新的内容依然陈旧，知识也随之逐渐腐朽。

这两者本质上都不是写作问题，而是关系问题：哪些文件属于同一个概念，哪些概念会受到代码变更的影响，这些都无法通过孤立地查看文件来可靠地判定。

我们使用代码图谱来为这些决策提供稳定的基础。

# 构建：Leiden 划定边界，PageRank 挑选文件

首先，我们将 NeuG 的代码库构建为一张图：文件和函数作为节点，函数调用关系作为边。在符号级别，这为我们提供了约 28,000 个节点和 52,501 条边。

但符号级别对于概念分组来说粒度太细——文件级别效果更好。因此，我们将符号图聚合为文件级视图：“文件包含函数，函数相互调用”折叠为文件到文件的关系，从而生成 1,423 个文件节点和 3,869 条边。

此视图仅用于计算，因此我们使用 NeuG v0.1.3 的 COPY TEMP 将其作为临时图导入——运行分析，丢弃临时数据，不会对持久化图造成污染。

然后我们在文件级图上进行两项操作：

**首先，使用 Leiden 社区发现来定义概念边界。** 紧密相关的文件自然会聚到同一个社区中，独立于目录结构。

```cypher
CALL leiden('code_graph', {concurrency: 1})
YIELD node, community
RETURN node.name, community
```

以 NeuG 代码库中的一个典型社区为例：**type-and-value-system**。它包含 187 个文件，跨越 6 个路径前缀。下图比较了这两种方法在 6 个代表性元素上的表现：图方法使用 Leiden 聚类将类型、值、类型转换和比较正确地分组到一个“类型系统”部分；而 LLM 方法遵循目录结构，将它们拆分到 `common-types` 和 `built-in-functions` 中——切断了语义联系。

![type-and-value-system 聚类对比](/images/blog/code-graph-wiki/clustering_comparison.png)

**其次，使用 PageRank 为每个概念组挑选核心文件。** 一旦定义了社区，LLM 应该读取哪些文件来编写 wiki？它通常依赖于启发式规则——比如挑选文件名较短的文件。图方法使用 PageRank 根据全局引用次数对文件进行排名，并直接呈现最重要的文件：

```cypher
CALL page_rank('code_graph', {max_iterations: 20})
YIELD node, rank
WITH node, rank WHERE node.community = 37
RETURN node.name, rank
ORDER BY rank DESC LIMIT 5;
```

对于 `cypher-parser` 部分，PageRank 的首选是 `transformer.h`（330 行，声明了所有 transform 方法，被许多文件引用）；而 LLM 选择了 `use_database.h`（39 行，1-2 次引用，选择它是因为文件名较短且它是一个 `.h`）。

PageRank 版本涵盖了 Transformer 类的 80 多个方法调度架构和运算符优先级链。LLM 选择的版本概述正确，但必须推断核心架构，让读者自己去查阅源代码。区别不在于写作风格，而在于证据：一个版本读取了支持该部分的文件，而另一个版本读取的仅仅是看起来相关的文件。

![PageRank 与 LLM 文件选择对比](/images/blog/code-graph-wiki/pagerank_vs_llm.png)

**第三，相同的分组可以被复现。** 图计算每次运行都会产生相同的输出；而 LLM 生成的 wiki 每次都会发生漂移：

![可复现性对比](/images/blog/code-graph-wiki/reproducibility.png)

# 更新：Leiden 分配新概念，Cypher 计算差异

构建过程解决了“首次如何拆分”的问题。但代码每天都在变化——知识库不能一劳永逸地拆分后就置之不理。

NeuG 提供了一种增量式的 **冻结分配 Leiden 算法**：现有节点保留其概念分配，仅对新内容进行重新聚类。以前是“编译器”的模块，之后依然是“编译器”。无漂移，完全支持差异比对。

```cypher
CALL leiden('code_graph', {concurrency: 1,
  initial_community_property: 'delta_comm'})
YIELD node, community, previous_community
RETURN node.id, community, previous_community;
```

**然后使用 Cypher 计算社区级别的差异**：按社区分组，精确衡量每个社区的变化——稳定/增长/新增。只有实际发生变化的社区才会被输入给 LLM；稳定的社区则直接原样复用。

```cypher
MATCH (n)
WITH n.community AS community, count(*) AS total,
     count(n.previous_community) AS old_members
RETURN community, total - old_members AS new_members,
  CASE WHEN old_members = 0 THEN 'new'
       WHEN old_members = total THEN 'stable'
       ELSE 'growth' END AS change_type;
```

例如，将一次 NeuG 版本更新（47 个变更文件，+14,243 / -61 行）与 wiki 进行对比分析：

LLM 方案：读取所有 35 个变更文件，逐一与 23 个章节进行对比。可能会标记 4 个需要更新，但其中两个是误报。

图方案：直接识别出 21 个零变更的概念（wiki 章节），以及 2 个包含新成员的概念——只有这两个章节需要增量更新。

# 在多次更新中保持知识库的一致性

图谱并不直接编写 Wiki。它解答了两个需要长期保持一致的问题：哪些证据定义了概念边界，以及代码变更后究竟哪些章节需要重写。

NeuG 基于代码关系计算边界与受影响区域。随后，LLM 会阅读相关代码并生成解释说明。其核心目的不仅在于生成高质量的初始版本，更在于历经多次更新后，依然保持概念结构的一致性，确保不遗漏任何已变更的知识。

如果你曾遇到过概念组漂移的问题，或者在代码变更后难以决定该更新哪些章节，欢迎分享你在项目中遇到的实际情况。
