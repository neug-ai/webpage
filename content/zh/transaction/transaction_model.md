# 事务模型

嵌入式模式（AP）和服务模式（TP）采用不同的事务模型。

## 共同的事务约定

嵌入式模式（AP）和服务模式（TP）都使用私有事务视图：

- 只读事务在其生命周期内固定一个一致的读取视图，并拒绝写入；
- 读写事务持有一个私有的写时复制（COW）视图。它可以读取自身已成功执行的写入，
  其他事务则继续读取已经提交的状态；
- 提交以原子方式发布全部变更。回滚、执行失败的语句或未提交的事务都不会发布部分
  COW 状态；
- 持久化数据库中的常规提交会将重做信息追加到预写日志（WAL）。重启时，NeuG 会恢复
  最近的检查点，并重放之后已经提交的 WAL 记录。

两种部署模式的差异在于如何协调并发工作，以及是否支持文件和批量语句。

## 嵌入式模式（AP）

嵌入式模式侧重可预测的本地执行和分析执行。多个读操作可以共享访问权限；修改数据、
模式或索引的操作则需要取得独占写入准入。显式读写事务会一直持有该准入权限，直到提交、
回滚或其连接关闭。

### 常规写入

NeuG 将常规写入应用到事务的私有 COW 视图，并把已经提交的变更记录到 WAL。只有提交
成功后，NeuG 才会发布该视图。无需在每次常规写入之后手动创建检查点。

### 文件与批量操作

嵌入式模式是唯一支持 `LOAD FROM` 和 `COPY` 语句的模式：

- `LOAD FROM` 为查询读取外部数据，不修改持久化数据库状态。
- `COPY ... TO` 导出数据，不修改持久化数据库状态。
- `COPY TEMP` 构建临时连接作用域的数据，不具备持久性。
- 持久化 `COPY ... FROM` 会更改数据库状态，并在整个操作期间使用独占准入。

对于持久化 `COPY ... FROM`，NeuG 会在私有克隆视图中准备并验证导入的数据。如果加载或验证失败，NeuG 将丢弃该视图并保持先前发布的数据库不变。在自动提交模式下，成功后 NeuG 会创建并持久化发布一个包含导入数据的检查点，然后才替换当前视图并报告成功。这种悲观准入加上检查点后发布的序列，即使对于大型导入也能保证原子性和持久性。持久化 `COPY ... FROM` 也可以在嵌入式读写显式事务中运行，此时检查点会推迟到 `commit()`，并且可以一次性覆盖多个 COPY 语句以及交错的普通写入；请参阅[显式事务](explicit_transactions.mdx)。

## 服务模式（TP）

服务模式面向并发的应用请求。它使用多版本并发控制（MVCC），因此其他事务提交时，
读操作仍可在一致的快照上继续运行。

读取和插入可以并发执行。更新已有状态、修改模式或修改索引的操作通过更新租约串行执行。
显式读写事务会一直持有所需的租约，直到提交或回滚。事务的变更在提交发布之前保持私有。

每次成功的常规写入都会记录到 WAL。服务模式的检查点维护会等待正在进行的工作完成，
暂时阻止新事务启动，发布新检查点，并将各执行槽位的 WAL 写入器切换到新的纪元，然后
才接纳更多工作。

服务模式不支持 `LOAD FROM` 和任何 `COPY` 语句。因此，长时间运行的文件 I/O 和
批量数据库替换不会进入在线 TP 请求路径。请先在嵌入式模式下准备或导入持久化数据库，
再以服务模式打开该数据库以处理并发工作负载。

## 检查点发布

手动 `CHECKPOINT` 会获取独占维护控制权，并等待进行中的工作完成。NeuG 压缩活跃状态，写入完整的清单，使清单及其 WAL 纪元持久化，然后原子性地替换 `CURRENT` 选择器。只有在发布之后，正常的事务准入才会恢复。

脏图模块和索引模块会接收新的不可变对象。干净模块可以继续引用现有对象，因此完整检查点标志着一个完整的运行时生命周期边界，而不一定需要重写每个对象。

持久嵌入式模式 `COPY ... FROM` 使用更窄的私有 COW 检查点路径。它原子性地发布已准备的导入，而无需破坏性地转储或重新打开活跃图。在自动提交模式下，此发布发生在语句报告成功之前；在显式读写事务中，它会延迟到 `commit()`，后者可以将多个 COPY 语句和交错写入作为一个检查点发布。`LOAD FROM`、`COPY ... TO` 和 `COPY TEMP` 不使用此持久发布路径，因为它们不提交持久的图状态。

## 磁盘布局

持久化数据库使用一个清单选择器、由多个清单共享的不可变对象、每个清单 ID 对应的一个
WAL 纪元，以及每次打开数据库时使用的一个临时工作区：

```text
data_dir/
├── checkpoint/
│   ├── CURRENT                 # decimal manifest ID + trailing newline
│   ├── manifests/<id>.manifest
│   └── objects/<object-id>
├── wal/<id>/                   # WAL epoch for manifest <id>
└── runtime/open-<id>/          # temporary files for one database open;
                                # <id> is an opaque unique suffix (a UUID)
```

`CURRENT` 是发布选择器。其内容是所选清单的十进制 ID，末尾跟一个换行符（例如
`3\n`），NeuG 会以原子方式替换它。已发布的清单包含 `v`、`base_ts`、`schema`
和 `modules`，也可能包含 `scalars`。模块描述符保存对象 ID，而不是绝对路径。
清单及其 WAL 纪元使用同一个 ID。

`base_ts` 是已经包含在清单中的最大事务时间戳。恢复时会从该时间戳之后开始重放所选
WAL 纪元。完整检查点会重置事务时间线，数据库重新打开时使用 `base_ts=0`。

检查点对象不可变，并且可以被多个清单引用。运行时工作区不属于检查点数据。每次打开
数据库都会拥有一个 `runtime/open-<id>/` 目录，关闭时只删除自己未被固定的工作区。

进程使用数据库期间，请勿编辑 `CURRENT`。选择其他清单属于离线恢复操作：停止所有
进程，备份 `checkpoint/` 和 `wal/`，并且只选择已经完整持久化、格式兼容、所需对象
和同 ID WAL 纪元均完整的清单。选择不一致或更早的纪元可能导致恢复失败，或丢弃之后
已经提交的状态。

## 恢复与检查点失败

启动时，NeuG 会打开 `CURRENT` 选择的清单，并重放其中尚未包含的已提交 WAL 记录。
未曾通过 `CURRENT` 发布的未完成检查点工作会被忽略。

如果失败发生在破坏性的检查点转储开始之前，打开的数据库仍可继续使用。数据库关闭期间，
`Close()` 会报告该失败，以便调用方修正问题并重试。如果关闭检查点在消耗活动图状态后
失败，当前打开的实例便无法安全地继续运行：NeuG 会完成清理、将其标记为已关闭并报告
错误。之后重新打开数据库时，仍可从此前发布的检查点和已提交的 WAL 中恢复。

## 垃圾回收与磁盘空间回收

只有在退役的清单、WAL 纪元、不可变对象和遗留的运行时工作区既不是当前版本，也未被
活动检查点引用保留时，垃圾回收才会将其删除。垃圾回收会在以读写方式打开数据库、手动
执行 `CHECKPOINT` 成功以及关闭数据库时运行。

因此，删除行或删除表不会立即减少磁盘占用。以只读方式打开数据库时从不运行垃圾回收；
下次以读写方式打开时，才会回收只读进程崩溃后遗留的过期工作区。

## 升级旧版检查点目录

如果 `CURRENT` 不存在，首次以读写模式打开将升级最新的有效的已发布 v1 `checkpoint-N` 代。NeuG 会导入其不可变快照文件，将该代保留为新的清单和 WAL 纪元 ID，发布一个 v2 清单，然后执行常规恢复。

在新的 `CURRENT` 实现持久化之前，旧版目录保持不变。在发布前发生崩溃会使旧版检查点仍可使用，并且下一次以读写模式打开时会重试。成功打开并恢复后，常规垃圾回收会移除旧版的 `checkpoint-N` 和 `checkpoint-N.next` 目录。仅包含旧版数据的数据库必须先以读写模式打开一次，然后才能以只读模式打开。系统会拒绝不支持的旧版元数据，而不是进行猜测。
