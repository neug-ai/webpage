# 事务模型

嵌入式模式（AP）和服务模式（TP）采用不同的事务模型。

## 共同的事务约定

嵌入式模式（AP）和服务模式（TP）都使用私有事务视图：

- 只读事务在其生命周期内固定一个一致的读取视图，并拒绝写入；
- 读写事务持有一个私有的写时复制（COW）视图。它可以读取自身已成功执行的写入，
  其他事务则继续读取已经提交的状态；
- 提交以原子方式发布全部变更。回滚、执行失败的语句或未提交的事务都不会发布部分
  COW 状态；
- 持久化数据库中的常规提交会将重做信息追加到预写日志（WAL）。重启时，NeuG 会恢复
  最近的检查点，并重放之后已经提交的 WAL 记录。

两种部署模式的差异在于如何协调并发工作，以及是否支持文件和批量语句。

## 嵌入式模式（AP）

嵌入式模式侧重可预测的本地执行和分析执行。多个读操作可以共享访问权限；修改数据、
模式或索引的操作则需要取得独占写入准入。显式读写事务会一直持有该准入权限，直到提交、
回滚或其连接关闭。

### 常规写入

NeuG 将常规写入应用到事务的私有 COW 视图，并把已经提交的变更记录到 WAL。只有提交
成功后，NeuG 才会发布该视图。无需在每次常规写入之后手动创建检查点。

### 文件与批量操作

嵌入式模式是唯一支持 `LOAD FROM` 和 `COPY` 语句：

- `LOAD FROM` 为查询读取外部数据，且不修改持久
  数据库状态。
- `COPY ... TO` 导出数据，且不修改持久化数据库状态。
- `COPY TEMP` 构建临时的连接作用域数据，且不具备持久性。
- 持久化的 `COPY ... FROM` 会更改数据库状态，并在整个操作过程中使用独占
  准入。

对于持久化的 `COPY ... FROM`，NeuG 会在私有克隆视图中准备并验证导入的数据
。如果加载或验证失败，NeuG 会丢弃该
视图并保持先前发布的数据库不变。在自动提交模式下，
成功时 NeuG 会创建并持久发布一个包含导入内容的检查点，
然后再替换当前视图并报告成功。这种悲观
准入加上检查点后发布的顺序，即使对于大型导入也能保证原子性和
持久性。自 v0.2.1 起，持久化的 `COPY ... FROM`
可以改为在嵌入式读写显式事务中运行，其中
检查点会延迟到 `commit()`，并且可能同时覆盖多个 COPY 语句和
交错的普通写入操作；请参阅
[显式事务](explicit_transactions.mdx)。

## 服务模式 (TP)

> **注意：** 服务模式需要 HTTP 服务器组件，该组件目前尚未在 Windows 上构建。请在 Linux 或 macOS 主机（或 WSL 下）上运行该服务。

服务模式专为并发应用请求而设计。它使用
多版本并发控制 (MVCC)，以便在其他事务提交时，读取操作可以在一致的
快照上继续。

读取和插入工作可以并发进行。更新现有
状态、更改模式或更改索引的操作通过更新租约进行串行化。
显式读写事务会保留所需的租约，直到提交或
回滚。其更改保持私有，直到提交将其发布。

每次成功的普通写入都会记录在 WAL 中。服务模式检查点
维护会等待进行中的工作，暂时阻止新事务
启动，发布新的检查点，并在允许更多工作之前将执行槽 WAL
写入器轮转到新纪元。

服务模式拒绝 `LOAD FROM` 以及每个 `COPY` 语句。因此，长时间运行的文件
I/O 和批量数据库替换将保持在在线 TP 请求
路径之外。在嵌入式模式中准备或导入持久化数据库，然后在
服务模式中打开它以处理并发工作负载。

## 检查点发布

手动`CHECKPOINT`获取独占的维护控制权并等待
进行中的工作完成。NeuG 压缩实时状态，写入完整的清单，
使清单及其 WAL 纪元持久化，然后原子地替换
`CURRENT`选择器。只有在发布之后，正常的事务准入
才会恢复。

脏图和索引模块接收新的不可变对象。干净模块可能
继续引用现有对象，因此完整的检查点标记了一个完整的
运行时生命周期边界，而不必重写每个对象。

持久化嵌入式模式`COPY ... FROM`使用更窄的私有写时复制检查点
路径。它原子地发布准备好的导入，而不会破坏性地转储
或重新打开实时图。在自动提交模式下，此发布发生在
语句报告成功之前；在显式读写事务中，它被
延迟到`commit()`，它可能将多个 COPY 语句和
交错写入作为一个检查点发布。`LOAD FROM`, `COPY ... TO`，和`COPY TEMP`
不使用此持久化发布路径，因为它们不提交持久化的
图状态。

## 磁盘布局

持久化数据库使用一个清单选择器、由多个清单共享的不可变对象、每个清单 ID 对应的一个
WAL 纪元，以及每次打开数据库时使用的一个临时工作区：

```text
data_dir/
├── checkpoint/
│   ├── CURRENT                 # decimal manifest ID + trailing newline
│   ├── manifests/<id>.manifest
│   └── objects/<object-id>
├── wal/<id>/                   # WAL epoch for manifest <id>
└── runtime/open-<id>/          # temporary files for one database open;
                                # <id> is an opaque unique suffix (a UUID)
```

`CURRENT` 是发布选择器。其内容是所选清单的十进制 ID，末尾跟一个换行符（例如
`3\n`），NeuG 会以原子方式替换它。已发布的清单包含 `v`、`base_ts`、`schema`
和 `modules`，也可能包含 `scalars`。模块描述符保存对象 ID，而不是绝对路径。
清单及其 WAL 纪元使用同一个 ID。

`base_ts` 是已经包含在清单中的最大事务时间戳。恢复时会从该时间戳之后开始重放所选
WAL 纪元。完整检查点会重置事务时间线，数据库重新打开时使用 `base_ts=0`。

检查点对象不可变，并且可以被多个清单引用。运行时工作区不属于检查点数据。每次打开
数据库都会拥有一个 `runtime/open-<id>/` 目录，关闭时只删除自己未被固定的工作区。

进程使用数据库期间，请勿编辑 `CURRENT`。选择其他清单属于离线恢复操作：停止所有
进程，备份 `checkpoint/` 和 `wal/`，并且只选择已经完整持久化、格式兼容、所需对象
和同 ID WAL 纪元均完整的清单。选择不一致或更早的纪元可能导致恢复失败，或丢弃之后
已经提交的状态。

## 恢复与检查点失败

启动时，NeuG 会打开 `CURRENT` 选择的清单，并重放其中尚未包含的已提交 WAL 记录。
未曾通过 `CURRENT` 发布的未完成检查点工作会被忽略。

如果失败发生在破坏性的检查点转储开始之前，打开的数据库仍可继续使用。数据库关闭期间，
`Close()` 会报告该失败，以便调用方修正问题并重试。如果关闭检查点在消耗活动图状态后
失败，当前打开的实例便无法安全地继续运行：NeuG 会完成清理、将其标记为已关闭并报告
错误。之后重新打开数据库时，仍可从此前发布的检查点和已提交的 WAL 中恢复。

## 垃圾回收与磁盘空间回收

只有在退役的清单、WAL 纪元、不可变对象和遗留的运行时工作区既不是当前版本，也未被
活动检查点引用保留时，垃圾回收才会将其删除。垃圾回收会在以读写方式打开数据库、手动
执行 `CHECKPOINT` 成功以及关闭数据库时运行。

因此，删除行或删除表不会立即减少磁盘占用。以只读方式打开数据库时从不运行垃圾回收；
下次以读写方式打开时，才会回收只读进程崩溃后遗留的过期工作区。

## 升级旧版检查点目录

如果没有 `CURRENT`，首次以读写方式打开数据库时会升级最新且有效的已发布 v1
`checkpoint-N` 世代。NeuG 会导入其中的不可变快照文件，保留该世代作为新的清单和
WAL 纪元 ID，发布 v2 清单，然后执行常规恢复。

在新的 `CURRENT` 持久化之前，旧版目录不会发生变化。如果发布前崩溃，旧版检查点仍
可使用，下次以读写方式打开时会重试。成功打开并完成恢复后，常规垃圾回收会删除旧版
`checkpoint-N` 和 `checkpoint-N.next` 目录。仅含旧版数据的数据库必须先以读写模式
打开一次，之后才能以只读模式打开。NeuG 会拒绝无法支持的旧版元数据版本，而不会猜测其格式。
