# 工作原理

本页介绍了 NeuG 如何在内部实现事务和检查点。
本文面向需要了解这些保证背后的
机制的高级用户和运维人员。如需了解日常用法，请参阅
[事务管理](transaction.mdx) 和 [检查点](checkpoint.md)。

## 事务模型内部机制

NeuG 使用写时复制（COW）视图将读操作与写操作分离：

- **只读**事务在其生命周期内固定一个读视图，并拒绝
  写入操作。
- **读写**事务拥有一个私有的 COW 视图，读取自身成功的
  写入，并且仅在提交成功时才发布其更改。失败或
  未提交的 COW 更改永远不会被发布。

**嵌入式（AP）准入。** 读写事务在其整个生命周期内持有排他性的 AP
准入：所有其他 AP 操作都会等待，直到它
提交、回滚或其连接关闭。嵌入式 READ_WRITE 模式还
只允许一个公共 `Connection` 同时，因此 AP 写入实际上是
串行化的。

**服务（TP）更新租约。** 读写事务持有 TP 更新
租约。在持有租约期间，其他读写事务无法开始，并且
普通的插入和更新操作会等待其完成；读操作在
一致的 MVCC 快照上保持并发。成功的提交会追加并发布一个 WAL
提交。

**WAL。** 已提交的普通写入会将逻辑重做追加到 WAL 中，并在
重启时重放。当前的 WAL 格式足以满足正常重放，但
其最终帧格式、损坏处理以及提交未知恢复规则
仍在完善中。在批量加载后需要持久化物化
检查点的应用程序，应使用 [检查点](checkpoint.md) 中描述的检查点生命周期。

## 检查点磁盘布局

持久化数据库使用一个清单选择器、由清单共享的不可变对象、每个清单 ID 一个 WAL 纪元，以及每次数据库打开时的一个临时工作区：

```text
data_dir/
├── checkpoint/
│   ├── CURRENT                 # decimal manifest ID + trailing newline
│   ├── manifests/<id>.manifest
│   └── objects/<object-id>
├── wal/<id>/                   # WAL epoch for manifest <id>
└── runtime/open-<id>/          # temporary files for one database open;
                                # <id> is an opaque unique suffix (a UUID)
```

`CURRENT` 是唯一的发布选择器。其内容是所选
清单的十进制 ID，后跟一个尾部换行符（例如 `3\n`)，
通过原子重命名写入；运维人员可以直接检查它。重写它是一个
离线恢复操作：首先停止使用数据库的每个进程并
备份 `checkpoint/` 和 `wal/`，然后仅选择一个完全持久化的清单
，其引用的对象和相同 ID 的 WAL 纪元是完整且兼容的。
选择不一致或较旧的纪元可能会导致恢复失败或丢弃稍后
提交的状态。已发布的清单具有必需的字段 `v`, `base_ts`,
`schema`，和 `modules`；它还可能包含 `scalars`。模块描述符持久化
对象 ID，而不是绝对路径。相同的 ID 命名清单及其 WAL 纪元。
`base_ts` 是清单已表示的最高事务时间戳，因此恢复从 `base_ts + 1`。完整
检查点使用 `base_ts=0` 并在重新打开后重置事务时间线。

检查点对象是不可变的，并且可能被多个清单引用。
运行时文件不是检查点数据：每次打开数据库都会获得其专属的
`runtime/open-<id>/` 目录（后缀是一个不透明的唯一 ID，而不是
时间戳或清单 ID），关闭该数据库仅会移除其自己的
未固定的工作区。

## 检查点协议

手动`CHECKPOINT`首先获取独占的检查点维护控制权，并
等待进行中的工作完成（请参阅
[并发](checkpoint.md#concurrency)）。它保留了现有的
全量检查点行为：压缩活动图，破坏性地转储它，发布
完整的清单，并重新打开图和分配器。只有脏图和
索引模块需要新的不可变对象；干净模块的描述符可以继续
引用现有对象。清单及其 WAL 纪元在`CURRENT`被原子替换。

持久化 AP-direct `COPY`和批量插入使用更
窄的私有 COW 协议。该语句
在克隆的图中准备所有更改，仅在该克隆上执行现有的消耗性
脏模块转储/重新打开，然后发布暂存清单
并原子替换当前图。它不会压缩或重新打开
已发布的图或分配器。每个成功的持久化批量语句
都会推进检查点 ID，并将活动的 WAL 写入器轮转到新纪元。

手动检查点发布后，NeuG 从新检查点重新打开活动图和分配器
。在服务模式下，每个执行槽的 WAL 写入器随后
轮转到新纪元。最后，重置事务时间线并允许新
事务。这些步骤都在检查点屏障
仍然保持时运行。

恢复和关闭检查点使用相同的压缩、破坏性转储。
恢复在数据库开始提供服务之前重新打开图和分配器；
关闭则持久化而不重新打开。

在破坏性转储开始之前，关闭检查点失败会使
打开的数据库保持可用，并且`Close()`报告失败，以便调用者可以纠正
它并重试。一旦转储消耗了活动图状态，对于该打开的实例，失败就不可
重试：`Close()`完成资源和锁清理，
将数据库标记为已关闭，并重新抛出失败。稍后新的`Open()`仍然
可以使用之前发布的检查点。

"全量"描述了运行时生命周期边界；它不需要重写
每个干净的不可变对象。因此，检查点磁盘增长是由
重写的模块加上活动引用保留的对象驱动的。根据崩溃后可接受的重放工作量和 WAL 增长来安排检查点
，而不是固定的紧密间隔。

## 垃圾回收与磁盘空间回收

已废弃的清单、WAL 纪元、不可变对象以及被遗弃的
`runtime/open-<id>/` 工作区由垃圾回收机制移除，该机制仅在以下三个时间点运行：读写数据库打开、成功的手动
`CHECKPOINT`，以及数据库关闭。因此，删除行或删除表不会
减少磁盘占用，直到达到这些时间点之一。垃圾回收
仅在清单、WAL 纪元和对象既非
当前使用，也未被活跃的检查点引用保留时，才会将其移除。

只读打开从不运行垃圾回收。纯只读部署
会累积陈旧的 `runtime/open-<id>/` 被崩溃的
只读进程遗留下来的工作区；下一次读写打开会回收它们。

## 升级旧版检查点目录

当 `CURRENT` 缺失时，首次读写打开会自动升级
最新的有效已发布 v1 `checkpoint-N` 代。NeuG 将其不可变的
快照文件导入 `checkpoint/objects/`，将其代保留为新的
清单和 WAL 纪元 ID，并发布带有 `base_ts=0` 的 v2 清单；然后正常
恢复会重放每个旧版 WAL 记录。文件在安全时使用硬链接，
否则进行复制。

在新 `CURRENT` 被持久
发布之前，旧目录不会被更改。发布前的崩溃会使旧版检查点保持可用，
并且下一次读写打开会重试。数据库成功打开并恢复
后，正常的垃圾回收会移除旧的 `checkpoint-N` 和
`checkpoint-N.next` 目录，使升级成为单向操作。纯旧版
数据库无法以只读方式打开：请以读写模式打开一次以执行
升级。旧版 `meta` 除 v1 之外的版本会被拒绝，而不是
进行猜测。
