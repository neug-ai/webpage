# 概览

NeuG 在两种部署模式下提供相同的事务保障：面向进程内分析工作负载（AP）的
**嵌入式模式**，以及面向并发事务工作负载（TP）的**服务模式**。

在应用层，两种模式遵循相同的基本保障和使用规则：

- 每条查询都在事务中运行；
- 默认采用自动提交；
- 可以通过显式事务将多条查询组合为一个工作单元；
- 成功提交具有原子性，并与其他事务隔离；
- 持久化数据库中已提交的变更可在重启后恢复。

两种模式面向应用的主要能力差异在于文件 I/O：`LOAD FROM` 和所有 `COPY`
语句仅在嵌入式模式下可用，服务模式不支持这些语句。

## NeuG 中的 ACID

两种部署模式提供相同的、用户可观察到的 ACID 保障：

| 特性 | 行为 |
|------|------|
| **原子性（Atomicity）** | 一个事务要么提交全部变更，要么不发布任何变更。 |
| **一致性（Consistency）** | 在变更可见之前，NeuG 会检查模式约束、主键唯一性和边的参照完整性。 |
| **隔离性（Isolation）** | 事务看到一致的数据库视图；并发执行不会暴露部分变更。 |
| **持久性（Durability）** | 持久化数据库中的事务一旦提交，NeuG 就能在重启后恢复它。内存数据库不具备持久性。 |

有关这些保障背后的不同事务模型，请参阅[事务模型](transaction_model.md)。

## 选择部署模式

根据应用的连接方式，以及是否需要文件操作或批量操作来选择模式：

| | 嵌入式模式（AP） | 服务模式（TP） |
|---|----------------|----------------|
| **典型用途** | 分析、ETL、本地工具、批处理 | 交互式应用和网络服务 |
| **连接方式** | 进程内 `Connection` | 网络 `Session` |
| **客户端** | C++、Python、Node.js | Python、Java |
| **常规 Cypher** | 读取、插入、更新、删除以及模式和索引操作 | 相同 |
| **文件和批量语句** | 支持 `LOAD FROM`、`COPY FROM`、`COPY TEMP` 和 `COPY TO` | 不支持 |
| **显式事务** | 支持 | 支持 |

两种模式对常规 Cypher 查询采用相同的提交和回滚语义。在两种模式之间迁移应用时，
通常需要改变的是连接方式，而不是常规操作的提交和回滚方式。

## 运行事务

### 默认采用自动提交

除非已有显式事务处于活动状态，否则每次 `execute()` 或 `Query()` 调用都是一个独立事务：

```python
conn.execute("CREATE (p:Person {name: 'Alice'})")  # committed
conn.execute("CREATE (p:Person {name: 'Bob'})")    # committed separately
```

如果语句失败，对应的自动提交事务会回滚，其部分变更不会对外可见。

如果多条语句不需要作为一组共同成功或失败，自动提交是最简单的选择。

### 使用显式事务组合相关查询

当多条语句必须一起提交时，请使用显式事务：

```python
conn.begin_transaction()
try:
    conn.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    conn.execute("CREATE (:Person {name: 'Bob'})", access_mode="insert")
    conn.commit()
except Exception:
    conn.rollback()
    raise
```

只读显式事务会拒绝写入。读写事务可以读取自身已成功执行的写入，并且只有提交后，
这些变更才对其他事务可见。

有关各客户端 API、受支持的客户端、不允许执行的语句以及仅可回滚状态，请参阅
[显式事务](explicit_transactions.mdx)。

## 访问模式

可选参数 `access_mode` 用于说明查询执行的操作类型：

| 模式 | 别名 | 用途 |
|------|------|------|
| `read` | `r` | 不修改数据的查询 |
| `insert` | `i` | 创建新的节点和边 |
| `update` | `u` | 更新、删除和 `MERGE` |
| `schema` | `s` | 创建或修改节点表和边表 |

如果省略 `access_mode`，NeuG 会根据查询推断访问模式。如果显式指定的模式不允许执行该查询，
NeuG 将返回错误。

在服务模式下，指定范围最小且正确的模式有助于 NeuG 高效调度并发请求。在嵌入式模式下，
通常让 NeuG 自动推断即可；应用也可以显式指定模式来校验自身意图。

`CHECKPOINT` 是管理语句。它以 `update` 模式自动提交，并且不能在显式事务中运行。
请参阅[检查点](checkpoint.md)。

## 模式特有限制：文件 I/O

`LOAD FROM` 和所有 `COPY` 语句仅在嵌入式模式下可用，并且必须以自动提交方式运行。
服务模式不支持这些语句。持久化的 `COPY ... FROM` 具有原子性，只有在其检查点发布后
才会返回成功。

有关支持的语句和格式，请参阅[数据 I/O](../data_io/index.md)。

## 持久性与失败处理

持久化数据库中的常规提交写入无需手动执行 `CHECKPOINT` 即可恢复。自动提交语句失败时，
不会发布任何部分变更。显式事务内的数据库端操作失败后，该事务会进入仅可回滚状态；
必须先将其回滚，再执行其他查询。

有关事务失败规则，请参阅[显式事务](explicit_transactions.mdx)；有关持久化维护与恢复，
请参阅[检查点](checkpoint.md)。
