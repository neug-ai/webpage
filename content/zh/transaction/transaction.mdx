# 事务管理

NeuG 在两种部署模式下提供 ACID 事务：**嵌入式模式**，
专为分析处理（AP）优化，以及**服务模式**，专为
事务处理（TP）优化。自动提交是全局默认设置：每个查询
都是一个独立的事务，除非您将查询组合到一个显式事务中。

## 部署模式概览

请根据您的工作负载选择一种模式：

| | 嵌入式模式 (AP) | 服务模式 (TP) |
|---|--------------------|-------------------|
| **使用场景** | 分析、ETL、批处理 | 交互式应用、Web 服务 |
| **访问方式** | 进程内 `Connection` (C++, Python, Node.js) | 网络 `Session` (Python, Java) |
| **优化目标** | 最高单查询性能 | 并发读/插入吞吐量 |

每种模式提供的保证详见
[ACID 保证](#acid-guarantees)。

## ACID 保证

两种模式均提供完整的 ACID 保证；下表对其进行了总结，下方的注释则突出了两种模式的差异。

| 属性 | 嵌入式模式 (AP) | 服务模式 (TP) |
|----------|--------------------|-------------------|
| **原子性** | 全有或全无；失败的语句会自动回滚 | 与嵌入式模式相同 |
| **一致性** | 强制执行模式约束和参照完整性 | 与嵌入式模式相同 |
| **隔离性** | 排他写锁；读取并发运行 | MVCC：并发读取/插入；更新和 DDL 串行执行；排他检查点 |
| **持久性** | 已提交写入的 WAL；持久批量加载的检查点 | 自动 WAL 持久化 |

- **原子性。** 每条语句都是全有或全无。嵌入式模式的读写事务在私有的写时复制视图中累积其写入操作，并仅在提交时发布它们。在服务模式下，失败的语句会自动回滚，其他事务看不到任何部分状态。
- **一致性。** 模式约束和参照完整性在语句级别强制执行。无效操作（如重复的主键或违反的边约束）会被拒绝。
- **隔离性。** 嵌入式模式使用排他写锁；服务模式使用 MVCC。请参阅[隔离与并发](#isolation-and-concurrency)。
- **持久性。** 已提交的写入通过预写日志（WAL）进行持久化，并在重启时重放。请参阅[持久性与恢复](#durability-and-recovery)和[检查点](checkpoint.md)。

## 运行事务

### 自动提交（默认）

默认情况下，每个 `execute()` / `Query()` 调用都会作为自己的事务运行并
自动提交：

```python
conn.execute("CREATE (p:Person {name: 'Alice'})")  # committed immediately
conn.execute("CREATE (p:Person {name: 'Bob'})")    # committed immediately
```

### 显式事务

显式事务将多个查询组合为一个工作单元：开启事务，
在其中执行查询，然后提交或回滚。只读事务会固定
一个读视图并拒绝写入。读写事务会读取其自身
成功的写入，并且仅在提交成功时才发布它们。

对于各客户端的使用（C++、Python、Node.js、Java），各模式下的完整规则与
限制，以及失败/回滚行为，请参阅
[显式事务](explicit_transactions.mdx)。

## 隔离与并发

### 嵌入式模式 (AP)

嵌入式模式使用悲观排他锁，适用于单用户
分析型工作负载。读操作之间并发执行，但任何写入
语句（插入、更新、删除或模式变更）都会获取排他锁
并阻塞所有其他操作直至完成。

### 服务模式 (TP)

服务模式使用多版本并发控制 (MVCC) 提供
可串行化隔离，针对读取和插入占主导地位的图工作负载进行了调优：

| 操作 | 并发 |
|-----------|-------------|
| 读取 | 读取一致的快照；在活跃的插入/更新期间继续执行 |
| 插入 | 与读取和其他插入并发；如果正在进行更新则等待 |
| 更新 | 逐个执行；读取在快照上继续，插入和其他更新等待 |
| 模式 (DDL) | 与更新相同 |
| 检查点 | 独占维护；请参阅[检查点](checkpoint.md) |

> 在更新即将完成时到达的读取操作可能会短暂等待，通常
> 在毫秒级别。

```python
from neug import Session

session1 = Session("http://localhost:10000/")
session2 = Session("http://localhost:10000/")

# 并发：读操作不阻塞插入操作
session1.execute("MATCH (p:Person) RETURN count(p)", access_mode="read")
session2.execute("CREATE (p:Person {name: 'Bob'})", access_mode="insert")

# 序列化包含插入及其他更新；读取操作继续在快照上进行
session1.execute("MATCH (p:Person) SET p.updated = true", access_mode="update")
```

## 访问模式

指定一个 `access_mode` 来控制事务行为并优化
并发：

| 模式 | 别名 | 描述 |
|------|---------|-------------|
| `read` | `r` | 只读操作（无变更的 MATCH） |
| `insert` | `i` | 仅插入操作（创建新顶点/边） |
| `update` | `u` | 更新/删除操作（SET、DELETE、MERGE） |
| `schema` | `s` | 模式修改（创建/删除节点表或边表） |

如果未指定，NeuG 会推断模式。指定正确的模式可以在服务模式下实现
更好的并发优化。使用不支持计划操作的模式会返回错误。

在**服务模式**下，每种访问模式仅允许特定的操作：

| 指定模式 | 允许的操作 |
|----------------|--------------------|
| `read` | 读取 |
| `insert` | 插入 |
| `update` | 读取、插入、更新、模式修改、检查点 |
| `schema` | 读取、插入、更新、模式修改 |

`read` 和 `insert` 是局限于自身操作的狭义模式； `update`
和 `schema` 使用通用的串行更新路径并接受任何操作
（`update` 还允许 `CHECKPOINT`，而 `schema` 则不允许）。

`CHECKPOINT` 可以将 `update` 仅用作自动提交请求。当显式事务处于活动状态时，该请求会被拒绝
；请先结束事务。请参阅
[在显式事务内被拒绝的语句](explicit_transactions.mdx)。

在嵌入式模式下，除 `read` 之外的模式主要选择共享与排他
查询锁，而非不同的事务实现。显式 `read`
仍然拒绝写入。 `CHECKPOINT` 在两种模式下都是特殊的管理语句；请参阅[检查点](checkpoint.md)了解其接受的访问模式和
`EXPLAIN`/`PROFILE` 行为。

```python

# 最佳实践：将访问模式与操作相匹配
conn.execute("MATCH (n) RETURN n", access_mode="read")                  # 仅读锁
conn.execute("CREATE (p:Person {name: 'Alice'})", access_mode="insert")  # 插入锁

# 可行但非最优：用于读取的更新模式进入了更新路径
conn.execute("MATCH (n) RETURN n", access_mode="update")
```

## 持久性与恢复

已提交的写入会自动持久化并在重启时恢复；无需手动
检查点即可保证持久性。内存数据库不具备持久性，因为
其数据仅存在于易失性内存中。

**嵌入式模式。** 已提交的常规写入会将逻辑重做追加到 WAL 中，并
在正常重启时重放。一个持久的 `COPY ... FROM` 在报告成功前会发布
检查点；`COPY TEMP` 保留在内存中，并在
数据库关闭时丢失。启动时，NeuG 会加载由
`CURRENT` 选择，并重放该检查点的 `base_ts` 之后已提交的 WAL 记录；
失败或未提交的写时复制更改永远不会被发布。

**服务模式。** 每条语句在完成前都会记录到 WAL 中。
崩溃恢复会自动重放 WAL：未提交的操作会被回滚
，数据库会恢复到其最后的一致状态，无需手动
干预。

可选的检查点会合并 WAL 并减少恢复期间
重放的数据量，并使持久批量加载具备持久性。请参阅
[检查点](checkpoint.md) 了解检查点生命周期、并发和
故障行为。

## 最佳实践

以下建议总结了本页描述的行为。有关
终止、仅回滚状态以及显式
事务的各模式并发的完整规则，请参阅[显式事务](explicit_transactions.mdx)。

### 两种模式

- **默认使用自动提交。** 除非多个语句必须
  同时成功或失败，否则请依赖自动提交；仅为该分组开启显式事务。
- **使访问模式与操作相匹配。** 传递 `read` / `insert` / `update`
  / `schema`，以便 NeuG 选择最窄的路径。作为 `update` 发出
  的读取依然有效，但会进入串行化更新路径；请参阅[访问模式](#access-modes)。
- **在两条路径上及时结束显式事务。** 始终在 `try`/`finally`（或所用语言的等效方法）中提交或回滚。保持打开状态的读写
  事务会持有租约并阻塞其他工作。
- **切勿将 Cypher `BEGIN` / `COMMIT` / `ROLLBACK` 作为查询提交。** 请使用
  客户端的事务控制方法；Cypher 形式会使事务
  变为仅可回滚。

### 嵌入式模式

- **使用 `COPY ... FROM` 进行批量加载，而不是逐行插入。** 每个持久化
  `COPY` 在成功时会发布自己的检查点，并且比许多
  单行写入快得多；请参阅[持久性与恢复](#durability-and-recovery)。
- **保持读写事务简短。** 读写事务在其整个生命周期内持有
  排他性的 AP 准入，因此所有其他 AP 操作
  都会等待，直到它提交、回滚或其连接关闭。没有
  超时限制——请自行结束。
- **以只读方式运行分析查询。** 读取操作彼此并发运行
  并提供最佳的单查询吞吐量；将写入操作保留给加载和更新
  阶段。
- **完成后关闭连接和数据库**，以便刷新挂起的状态
  并释放锁。

```python
import neug

db = neug.Database("/path/to/database")
conn = db.connect()

# 创建模式；常规已提交的写入由WAL支持
conn.execute("CREATE NODE TABLE Person(id INT64, name STRING, PRIMARY KEY(id))")
conn.execute("CREATE NODE TABLE Company(id INT64, name STRING, PRIMARY KEY(id))")
conn.execute("CREATE REL TABLE WORKS_AT(FROM Person TO Company)")

# 每个持久化的 COPY ... FROM 在成功时都会发布其自身的检查点
conn.execute("COPY Person FROM 'employees_batch1.csv'")
conn.execute("COPY Person FROM 'employees_batch2.csv'")
conn.execute("COPY Company FROM 'companies.csv'")
conn.execute("COPY WORKS_AT FROM 'employment.csv'")

# 运行分析查询（只读，高性能）
result = conn.execute("MATCH (p:Person)-[:WORKS_AT]->(c:Company) RETURN c.name, count(p)")

conn.close()
db.close()
```

### 服务模式

- **每个客户端工作线程使用一个 `Session`。**一个 `Session` 最多同时拥有一个显式
  事务；切勿通过同一
  会话发出并发请求。
- **指定 `access_mode` 以保持读取和插入并发。**读取在
  一致的快照上运行，不会阻塞插入，因此让它们保持在窄
  `read` / `insert` 路径；请参阅[隔离与并发](#isolation-and-concurrency)。
- **在高并发场景中保持更新操作简短。**更新和 DDL 会
  串行化执行并持有 TP 更新租约：当一个执行时，其他插入和
  更新操作会等待（读取保持并发）。
- **始终关闭会话，最好在 `finally` 中。**关闭操作会尝试回滚
  任何打开的事务。被放弃的读写事务会保留更新
  租约，并延迟常规 TP 写入，直到服务释放它。

```python
from neug import Session

session = Session("http://localhost:10000/")

try:
    # Reads and inserts can be concurrent across sessions
    session.execute("CREATE (p:Person {name: 'Alice'})", access_mode="insert")

    # Reads don't block inserts
    result = session.execute("MATCH (p:Person) RETURN count(p)", access_mode="read")

    # Updates are serialized; keep them short in high-concurrency scenarios
    session.execute(
        "MATCH (p:Person) WHERE p.name = 'Alice' SET p.verified = true",
        access_mode="update",
    )
finally:
    session.close()
```

## 附录

### 设计说明

NeuG的事务模型反映了基于图工作负载
特性的权衡：图工作负载以读操作和插入操作为主，
而更新和模式变更相对较少；分析型
工作负载优先考虑单查询吞吐量；事务型工作负载需要
具备强隔离性的并发读/插入性能。与“一刀切”的
系统不同，NeuG提供了适用于相应工作负载的保证，从而在
简洁性、性能和正确性之间取得平衡。

### 版本历史

在 v0.2 之前，NeuG 仅提供隐式的自动提交模型，没有显式的
事务原语，并且对于大型 AP 写入无法完全保证
语句级原子性；应用程序使用检查点作为诸如 `COPY`。自 v0.2 起，常规写入使用私有的
写时复制图和 WAL，[显式事务](explicit_transactions.mdx)
在受支持的客户端中可用，并且持久性不再依赖于
手动检查点。

### 路线图

- 为嵌入式模式提供更透明的恢复诊断
- 用于高效增量持久化的 Delta 检查点
- 缩短大型数据集的检查点阻塞时间
- 策略驱动的周期性检查点
