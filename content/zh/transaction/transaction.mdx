# 概述

NeuG 在两种部署模式下提供相同的事务保证：
**嵌入式模式**用于进程内分析工作负载 (AP)，**服务模式**
用于并发事务工作负载 (TP)。

在应用层，共享以下保证和基本使用规则：

- 每个查询都在事务中运行；
- 默认启用自动提交；
- 多个查询可以组合在一个显式事务中；
- 成功的提交具有原子性，并与其他事务隔离；
- 持久化数据库中已提交的更改在重启后依然存在。

面向应用的主要功能差异在于文件 I/O: `LOAD FROM` 且每个
`COPY` 语句仅在嵌入式模式下可用。服务模式不
支持这些语句。

## NeuG 中 ACID 的含义

两种部署模式提供相同的用户可见 ACID 保证：

| 保证 | 行为 |
|-----------|----------|
| **原子性** | 事务要么提交其所有更改，要么不发布任何更改。 |
| **一致性** | 在更改变得可见之前，会检查模式约束、主键唯一性和边参照完整性。 |
| **隔离性** | 事务观察到一致的数据库视图；并发执行不会暴露部分更改。 |
| **持久性** | 一旦事务在持久化数据库中提交，NeuG 就可以在重启后恢复它。内存数据库不具备持久性。 |

有关这些保证背后的不同事务模型，请参阅
[事务模型](transaction_model.md)。

## 选择部署模式

根据应用程序的连接方式以及是否需要文件或批量操作来选择模式：

| | 嵌入式模式 (AP) | 服务模式 (TP) |
|---|--------------------|-------------------|
| **典型用途** | 分析、ETL、本地工具、批处理 | 交互式应用程序和网络服务 |
| **连接** | 进程内 `Connection` | 网络 `Session` |
| **客户端** | C++, Python, Node.js | Python, Java |
| **常规 Cypher** | 读取、插入、更新、删除、模式和索引操作 | 相同 |
| **文件和批量语句** | 支持 `LOAD FROM`, `COPY FROM`, `COPY TEMP`、`COPY TO` | 不支持 |
| **显式事务** | 支持 | 支持 |

相同的提交和回滚语义适用于两种模式下的常规 Cypher 查询。在模式之间移动应用程序通常会改变其连接方式，
而不会改变其提交和回滚常规工作的方式。

## 运行事务

### 自动提交是默认设置

每个 `execute()` 或 `Query()` 调用本身就是一个事务，除非有显式
事务处于活动状态：

```python
conn.execute("CREATE (p:Person {name: 'Alice'})")  # committed
conn.execute("CREATE (p:Person {name: 'Bob'})")    # committed separately
```

如果语句失败，该自动提交事务将被回滚，其任何部分更改均不会可见。

当语句不需要作为一个整体成功或失败时，自动提交是最简单的选择。

### 显式地对相关查询进行分组

当多个语句必须一起提交时，请使用显式事务：

```python
conn.begin_transaction()
try:
    conn.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    conn.execute("CREATE (:Person {name: 'Bob'})", access_mode="insert")
    conn.commit()
except Exception:
    conn.rollback()
    raise
```

只读显式事务会拒绝写入。读写事务可以看到其自身成功的写入，并且只有在提交后才会使这些写入对其他事务可见。

有关特定于客户端的 API、受支持的客户端、被拒绝的语句以及仅可回滚行为，请参阅[显式事务](explicit_transactions.mdx)。

## 访问模式

可选的 `access_mode` 告诉 NeuG 查询执行何种操作：

| 模式 | 别名 | 用途 |
|------|-------|---------|
| `read` | `r` | 不修改数据的查询 |
| `insert` | `i` | 创建新节点和边 |
| `update` | `u` | 更新、删除和 `MERGE` |
| `schema` | `s` | 创建或更改节点表和边表 |

如果 `access_mode` 被省略，NeuG 会从查询中推断它。显式
指定的模式如果不允许该查询，则会返回错误。

对于服务模式，指定最窄的正确模式有助于 NeuG 高效地调度
并发请求。在嵌入式模式中，推断通常
就足够了，除非应用程序想要显式验证其意图。

`CHECKPOINT` 是一条管理语句。它在自动提交下以
`update` 模式运行，并在显式事务内被拒绝。请参阅
[检查点](checkpoint.md)。

## 特定于模式的限制：文件 I/O

`LOAD FROM` 以及所有 `COPY` 语句仅在嵌入式模式下可用，并且
必须在自动提交中运行。服务模式不支持这些语句。持久的
`COPY ... FROM` 是原子的，并且仅在其检查点
发布后才返回成功。

有关支持的语句和格式，请参阅[数据 I/O](../data_io/index.md)。

## 持久性与故障

持久数据库中普通的已提交写入无需手动`CHECKPOINT`。失败的自动提交语句不会发布任何部分
更改。显式事务内部的数据库端故障会使其变为
仅可回滚状态；在发出另一个查询之前将其回滚。

请参阅[显式事务](explicit_transactions.mdx)了解事务故障
规则，以及[检查点](checkpoint.md)了解持久性维护和
恢复。
