# 概述

NeuG 在两种部署模式下提供相同的事务保证：用于进程内分析型工作负载（AP）的**嵌入式模式**和用于并发事务型工作负载（TP）的**服务模式**。

在应用层面，以下保证和基本使用规则是共享的：

- 每个查询都在一个事务中运行；
- 自动提交是默认行为；
- 多个查询可以组合在一个显式事务中；
- 成功提交具有原子性，并与其他事务隔离；
- 持久化数据库中已提交的更改在重启后仍然保留。

面向应用的主要能力差异在于文件 I/O：`LOAD FROM` 以及每个 `COPY` 语句仅在嵌入式模式中可用。服务模式不支持这些语句。

## NeuG 中的 ACID 含义

两种部署模式提供相同的用户可见 ACID 保证：

| 保证 | 行为 |
|-----------|----------|
| **原子性** | 事务要么提交其所有更改，要么不发布任何更改。 |
| **一致性** | 在更改变得可见之前，会检查模式约束、主键唯一性以及边参照完整性。 |
| **隔离性** | 事务观察到一致的数据库视图；并发执行不会暴露部分更改。 |
| **持久性** | 一旦事务在持久化数据库中提交，NeuG 可以在重启后恢复它。内存数据库不具备持久性。 |

有关这些保证背后的不同事务模型，请参阅
[事务模型](transaction_model.md)。

## 选择部署模式

根据应用程序的连接方式以及是否需要文件或批量操作来选择模式：

| | 嵌入式模式（AP） | 服务模式（TP） |
|---|--------------------|-------------------|
| **典型用途** | 分析、ETL、本地工具、批处理 | 交互式应用程序和网络服务 |
| **连接** | 进程内 `Connection` | 网络 `Session` |
| **客户端** | C++、Python、Node.js | Python、Java |
| **常规 Cypher** | 读取、插入、更新、删除、模式和索引操作 | 相同 |
| **文件和批量语句** | 支持 `LOAD FROM`、`COPY FROM`、`COPY TEMP` 和 `COPY TO` | 不支持 |
| **显式事务** | 支持 | 支持 |

相同的提交和回滚语义适用于两种模式下的常规 Cypher 查询。在模式之间迁移应用程序通常会改变其连接方式，而不会改变其提交和回滚常规工作的方式。

## 运行事务

### 自动提交是默认行为

除非存在活动的显式事务，否则每次 `execute()` 或 `Query()` 调用都是一个独立的事务：

```python
conn.execute("CREATE (p:Person {name: 'Alice'})")  # committed
conn.execute("CREATE (p:Person {name: 'Bob'})")    # committed separately
```

如果某条语句执行失败，该自动提交事务将被回滚，其部分更改均不可见。

当语句无需作为一组整体成功或失败时，自动提交是最简单的选择。

### 显式分组相关查询

当多条语句必须一起提交时，请使用显式事务：

```python
conn.begin_transaction()
try:
    conn.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    conn.execute("CREATE (:Person {name: 'Bob'})", access_mode="insert")
    conn.commit()
except Exception:
    conn.rollback()
    raise
```

只读显式事务会拒绝写入操作。读写事务可以看到自身成功的写入，但只有在提交后才会对其他事务可见。

有关特定于客户端的 API、支持的客户端、被拒绝的语句以及仅可回滚行为，请参阅
[显式事务](explicit_transactions.mdx)。

## 访问模式

可选的 `access_mode` 告诉 NeuG 查询执行何种类型的操作：

| 模式 | 别名 | 用途 |
|------|-------|---------|
| `read` | `r` | 不修改数据的查询 |
| `insert` | `i` | 创建新节点和边 |
| `update` | `u` | 更新、删除和 `MERGE` |
| `schema` | `s` | 创建或更改节点表和边表 |

如果省略 `access_mode`，NeuG 会从查询中推断它。如果显式指定的模式不允许该查询，则返回错误。

对于服务模式，指定最窄的正确模式有助于 NeuG 高效调度并发请求。在嵌入式模式下，除非应用程序希望显式验证其意图，否则推断通常已足够。

`CHECKPOINT` 是一条管理语句。它以 `update` 模式在自动提交下运行，并在显式事务中被拒绝。请参阅[检查点](checkpoint.md)。

## 模式特定限制：文件 I/O

`LOAD FROM` 和所有 `COPY` 语句仅在嵌入式模式下可用，且必须在自动提交中运行。服务模式不支持它们。持久化的 `COPY ... FROM` 是原子的，仅在其检查点发布后才返回成功。

有关支持的语句和格式，请参阅 [数据 I/O](../data_io/index.md)。

## 持久性与故障

在持久化数据库中，普通已提交的写入无需手动 `CHECKPOINT` 即可恢复。失败的自动提交语句不会发布任何部分更改。显式事务中的数据库端故障会使其变为仅可回滚；请在发出另一个查询之前将其回滚。

有关事务故障规则，请参阅 [显式事务](explicit_transactions.mdx)；有关持久性维护和恢复，请参阅 [检查点](checkpoint.md)。
