# 显式事务

显式事务将多条查询组合成一个工作单元。开始事务后执行查询，最后一起提交全部变更，
或将其全部回滚。

嵌入式模式（AP）和服务模式（TP）提供相同的显式事务保障，并采用相同的开始、提交和
回滚流程。两者使用的事务模型不同，拥有事务的客户端对象以及与网络有关的失败情况也
有所不同。

### 分组持久化 `COPY FROM` 语句

嵌入式读写事务可以将多个持久化 `COPY ... FROM` 语句分组。它们共享一个私有的 COW（写时复制）视图，因此后续的 COPY 可以使用早期 COPY 加载的顶点，并且对同一 `Connection` 的读取可以看到累积的数据。单个 COPY 语句不会发布检查点；`commit()` 通过一个检查点发布所有 COPY 更改，而 `rollback()` 则丢弃所有更改。

读取、普通 DML 和 DDL 可以与持久化 COPY 语句交错执行。如果任何 COPY 更改了持久化存储或创建了推断的持久化模式，则在提交时，一个检查点将发布事务的最终合并图。COPY 可以在事务内部推断并创建其自己的目标模式；该模式及其导入的数据将一起提交或回滚。用法请参阅 [Import without a predefined schema](../data_io/import_data.md)。

```python
# Create the target schema outside the COPY transaction.
conn.execute("CREATE NODE TABLE Person(id INT64, name STRING, PRIMARY KEY(id))")

conn.begin_transaction()
try:
    conn.execute("COPY Person FROM 'person_0.csv' (HEADER=true, DELIMITER=',')")
    conn.execute("COPY Person FROM 'person_1.csv' (HEADER=true, DELIMITER=',')")
    conn.commit()  # Publish both imports with one checkpoint.
except Exception:
    conn.rollback()
    raise
```

成功的 COPY 使其数据在事务内可用。仅在 `commit()` 成功后才会提交导入。`EXPLAIN` 可以检查写入计划而不更改数据或结束事务。`PROFILE` 执行其查询，因此适用与普通执行相同的限制。

根据可用内存和重试成本选择事务大小。私有更改保留在工作区中，直到事务结束，失败的批次必须完整重试。例如，在一个事务中加载顶点，在另一个事务中加载边，可以减少检查点频率，同时保持单独的重试边界。较少的检查点并不保证降低峰值内存；在比较批次大小时，请同时测量 COPY 阶段和提交阶段。

在端到端加载计时中包含 `begin_transaction()` 和 `commit()`。仅累加各个 COPY 持续时间会忽略最终检查点的成本。请分别报告 COPY 执行时间、提交时间以及直至提交的峰值内存。

### 读取、转换和导出外部数据

图只读 `LOAD FROM` 和 `COPY TO` 计划可以在嵌入式事务模式下运行。在读写事务中，`LOAD FROM` 还可以驱动普通的 `CREATE`、`MERGE`、`SET` 或 `DELETE` 子句。这些变更使用私有的写时复制（COW）视图，并遵循与普通 DML 相同的提交和回滚规则。读写事务还将其私有图视图提供给 `COPY TO`，因此它可以导出在同一事务中较早进行的更改。

外部文件不是事务性资源。图快照不会冻结由 `LOAD FROM` 读取的文件内容，如果图事务随后回滚，成功的 `COPY TO` 输出也不会被删除。内部查询更新图的 `COPY TO` 仍然不受支持。

### 使用临时图数据

`COPY TEMP` 可以在嵌入式读写事务中运行。该事务中的后续语句可以读取或修改临时图。回滚会丢弃它；提交使其可用，直到所属连接关闭。仅包含临时变更的事务不会写入预写日志（WAL）或发布检查点。

`COPY TEMP` 可以与持久化 DML、DDL 和持久化 `COPY FROM` 混合使用，顺序不限。所有变更都使用同一个私有图，并在一次提交时可见；回滚会同时丢弃临时变更和持久化变更。例如，加载到临时表中的行可以驱动 `MATCH ... CREATE` 进入持久化表。提交仅将持久化变更写入预写日志（WAL），或在发生持久化批量变更时发布检查点。临时对象保留在内存中，并被排除在预写日志（WAL）和检查点之外。

## 共同行为

显式事务在两种部署模式下遵循相同的规则：

- 每个 `Connection` 或 `Session` 同一时间只能有一个活动的显式事务，不支持嵌套事务；
- 只读事务在其生命周期内保持一致的读取视图，并拒绝写入；
- 读写事务可以读取自身已成功执行的写入；
- 变更只有在提交后才对其他事务可见；
- 回滚会丢弃该事务产生的所有变更；
- 不支持保存点和部分回滚；
- 不要通过同一个 `Connection` 或 `Session` 并发发送请求。

## 无法在显式事务中运行的语句

以下语句不得在显式事务处于活动状态时发出：

| 语句类别 | 示例 |
|-----------------|----------|
| 图变更导出 | 内部查询会更新图的 `COPY TO` |
| 数据库维护 | `CHECKPOINT` |
| 扩展管理 | `INSTALL`、`LOAD`、`UNINSTALL` |
| 变更型过程调用 | 会改变状态的 `CALL`，例如 `project_graph` 或 `drop_projected_graph` |
| Cypher 事务控制 | 作为查询文本提交的 `BEGIN`、`COMMIT`、`ROLLBACK` |

允许只读过程调用。

部署模式方面有一个重要区别：

- **嵌入式模式：** 在上述限制下，支持持久化 `COPY FROM`、`LOAD FROM` 读取和 DML、仅图读取的 `COPY TO` 以及 `COPY TEMP`。
- **服务模式：** 无论显式事务是否处于活动状态，均不支持 `LOAD FROM` 和所有 `COPY` 语句。这是[服务模式的文件 I/O 限制](../data_io/index.md)，而非显式事务限制。

## 失败与仅可回滚状态

如果一条语句到达 NeuG 并失败，其显式事务将变为**仅可回滚**。该事务无法提交；在发出另一个查询或开始另一个事务之前，请调用回滚。

这包括语法、语义分析、编译和执行错误、在只读事务中尝试写入，以及被上述规则拒绝的语句。

客户端在发送查询之前引发的验证错误不会改变事务状态。例如，Python 会对无效的 `access_mode` 抛出 `ValueError`，并保持事务可用。

对于嵌入式 COPY 事务，检查点准备失败并返回错误会使连接处于仅可回滚状态。一旦检查点处理开始消耗存储缓冲区，不可恢复的错误将终止进程，以防止进一步访问可能无效的内存中存储。现有的这一检查点限制也适用于显式 COPY 提交：它并不总能返回一个应用程序可以通过 `rollback()` 处理的异常。重新打开数据库后，在决定是否重试未观察到结果的提交之前，请检查恢复的数据。

## 客户端生命周期差异

两种模式的提交和回滚保障相同，但本地客户端与网络客户端在生命周期和失败情况上有所不同。

### 嵌入式客户端

- 事务保持活动状态，直到应用提交、回滚或关闭其 `Connection`；
- 事务没有超时时间；
- 关闭连接时会尝试回滚尚未结束的事务。

### 服务模式客户端

- 关闭 `Session` 时会尝试回滚其尚未结束的事务；
- 服务端可能使长时间无人使用的事务过期。下一次请求会报告该事务已过期，随后客户端会
  清除其本地事务句柄；
- 服务端关闭或网络故障后，本地客户端状态可能已经过期。请关闭该会话并创建新会话；
- 如果提交或回滚期间网络中断，最终结果可能无法确定。驱动不会重试，因为重放请求可能
  导致操作执行两次。

## 推荐用法

无论执行成功还是失败，都应结束事务：

```python
session.begin_transaction()
try:
    session.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    session.commit()
except Exception:
    session.rollback()
    raise
```

显式事务应尽量保持简短。如果多条语句不需要一起提交，请使用自动提交。
