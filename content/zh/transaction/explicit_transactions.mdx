# 显式事务

显式事务将多条查询组合成一个工作单元。开始事务后执行查询，最后一起提交全部变更，
或将其全部回滚。

嵌入式模式（AP）和服务模式（TP）提供相同的显式事务保障，并采用相同的开始、提交和
回滚流程。两者使用的事务模型不同，拥有事务的客户端对象以及与网络有关的失败情况也
有所不同。

### 分组持久化 `COPY FROM` 语句

> **版本说明：** 自 v0.2.1 起，嵌入式读写显式事务可以分组持久化 `COPY ... FROM` 语句——并将它们与读取、普通 DML/DDL 以及 `COPY TEMP` 交错——合并为在 `commit()` 发布的单个检查点。在早期版本中，持久化 `COPY ... FROM` 仅作为发布自身检查点的自动提交语句运行，并且显式事务会拒绝 `COPY`。

嵌入式读写事务可以分组多个持久化
`COPY ... FROM` 语句。它们共享一个私有的 COW 视图，因此后续的 COPY 可以
使用早期 COPY 加载的顶点，并且对同一 `Connection` 的读取可以
看到累积的数据。单独的 COPY 语句不会发布检查点；
`commit()` 使用一个检查点发布所有 COPY 更改，而 `rollback()`
会丢弃所有这些更改。

读取、普通 DML 和 DDL 可以与持久化 COPY 语句交错。
如果任何 COPY 更改了持久化存储或创建了推断的持久化模式，
一个检查点会在提交时发布事务的最终组合图。
COPY 可以在事务内部推断并创建其自己的目标模式；该
模式及其导入的数据会一起提交或回滚。有关用法，请参阅
[无需预定义模式的导入](../data_io/import_data.md)。

```python

# 在 COPY 事务之外创建目标模式。
conn.execute("CREATE NODE TABLE Person(id INT64, name STRING, PRIMARY KEY(id))")

conn.begin_transaction()
try:
    conn.execute("COPY Person FROM 'person_0.csv' (HEADER=true, DELIMITER=',')")
    conn.execute("COPY Person FROM 'person_1.csv' (HEADER=true, DELIMITER=',')")
    conn.commit()  # 使用一个检查点发布两次导入。
except Exception:
    conn.rollback()
    raise
```

成功的 COPY 会使其数据在事务内部可用。导入
仅在 `commit()` 成功。 `EXPLAIN` 可以检查写入计划，
而无需更改数据或结束事务。 `PROFILE` 执行其查询，
因此适用与普通执行相同的限制。

根据可用内存和重试成本选择事务大小。私有
更改保留在工作区中，直到事务结束，并且失败的批次必须
完整重试。例如，在一个事务中加载顶点，在另一个事务中加载边，
可以减少检查点频率，同时保持独立的重试
边界。较少的检查点并不能保证更低的峰值内存；在比较批次大小时，需同时测量
COPY 和提交阶段。

包括 `begin_transaction()` 和 `commit()` 在端到端加载计时中。仅对
各个 COPY 持续时间求和会忽略最终的检查点成本。分别报告 COPY
执行时间、提交时间以及直到提交的峰值内存。

### 读取、转换和导出外部数据

图只读 `LOAD FROM` 和 `COPY TO` 执行计划可以在嵌入式
事务模式下运行。在读写事务中，`LOAD FROM` 还可以驱动
常规的 `CREATE`, `MERGE`, `SET`，或 `DELETE` 子句。这些变更使用
私有的写时复制视图，并遵循与常规 DML 相同的提交和回滚规则。
读写事务还会将其私有图视图提供给 `COPY TO`，因此
它可以导出在同一事务中较早进行的更改。

外部文件不是事务资源。图快照不会
冻结由 `LOAD FROM`，并且成功的 `COPY TO`
输出不会在图事务随后回滚时被删除。一个 `COPY TO`
其内部查询更新图的 仍然不受支持。

### 处理临时图数据

`COPY TEMP` 可以在嵌入式读写事务中运行。该事务中的后续语句
可以读取或修改临时图。回滚会丢弃它；
提交则使其保持可用，直到所属连接关闭。仅包含临时
变更的事务不会写入 WAL 或发布检查点。

`COPY TEMP` 可以与持久化的 DML、DDL 和持久化 `COPY FROM` 以任意
顺序。所有更改都使用同一个私有图，并在一次
提交时变得可见；回滚会同时丢弃临时和持久化更改。例如，
加载到临时表中的行可以驱动 `MATCH ... CREATE` 到持久化
表中。提交时仅将持久化更改写入 WAL，或在发生持久化批量变更时发布检查点。临时对象保留在内存中，
并被排除在 WAL 和检查点之外。

### 服务模式

在服务模式下，每个 `Session` 同一时间最多持有一个事务。

## 共同行为

显式事务在两种部署模式下遵循相同的规则：

- 每个 `Connection` 或 `Session` 同一时间只能有一个活动的显式事务，不支持嵌套事务；
- 只读事务在其生命周期内保持一致的读取视图，并拒绝写入；
- 读写事务可以读取自身已成功执行的写入；
- 变更只有在提交后才对其他事务可见；
- 回滚会丢弃该事务产生的所有变更；
- 不支持保存点和部分回滚；
- 不要通过同一个 `Connection` 或 `Session` 并发发送请求。

## 无法在显式事务中运行的语句

在显式事务处于
活动状态时，不得发出以下语句：

| 语句类别 | 示例 |
|----------|------|
| 修改图的导出 | 一个 `COPY TO` 其内部查询更新图的语句 |
| 数据库维护 | `CHECKPOINT` |
| 扩展管理 | `INSTALL`, `LOAD`, `UNINSTALL` |
| 修改状态的存储过程调用 | 一个 `CALL`，例如 `project_graph` 或 `drop_projected_graph` 等改变状态的语句 |
| Cypher 事务控制 | `BEGIN`, `COMMIT`, `ROLLBACK` 作为查询文本提交 |

允许只读存储过程调用。

部署模式有一个重要区别：

- **嵌入式模式：** 持久化 `COPY FROM`, `LOAD FROM` 读取和 DML、
  仅读图的 `COPY TO`，以及 `COPY TEMP` 在上述限制下受支持。
- **服务模式：** `LOAD FROM` 以及所有 `COPY` 语句不受支持，
  无论显式事务是否处于活动状态。这是
  [服务模式下的文件 I/O 限制](../data_io/index.md)，
  而不是显式事务限制。

## 故障与仅可回滚状态

如果语句到达 NeuG 并失败，其显式事务将变为
**仅可回滚**。该事务无法提交；在发出
另一个查询或开始另一个事务之前，请调用回滚。

这包括语法、语义分析、编译和执行错误，
在只读事务中尝试的写入，以及被上述
规则拒绝的语句。

客户端在发送查询之前引发的验证错误不会
改变事务。例如，Python 会引发 `ValueError` 对于无效的
`access_mode` 并使事务保持可用。

对于嵌入式 COPY 事务，返回
错误的检查点准备失败会使连接变为仅可回滚。一旦检查点处理开始
消耗存储缓冲区，不可恢复的错误将终止该进程，以
防止进一步访问可能无效的内存存储。此现有的
检查点限制也适用于显式 COPY 提交：它并不总是能
返回应用程序可以使用 `rollback()`。在
重新打开数据库后，检查恢复的数据，然后再决定是否重试
未观察到结果的提交。

## 客户端生命周期差异

两种模式的提交和回滚保障相同，但本地客户端与网络客户端在生命周期和失败情况上有所不同。

### 嵌入式客户端

- 事务保持活动状态，直到应用提交、回滚或关闭其 `Connection`；
- 事务没有超时时间；
- 关闭连接时会尝试回滚尚未结束的事务。

### 服务模式客户端

- 关闭 `Session` 时会尝试回滚其尚未结束的事务；
- 服务端可能使长时间无人使用的事务过期。下一次请求会报告该事务已过期，随后客户端会
  清除其本地事务句柄；
- 服务端关闭或网络故障后，本地客户端状态可能已经过期。请关闭该会话并创建新会话；
- 如果提交或回滚期间网络中断，最终结果可能无法确定。驱动不会重试，因为重放请求可能
  导致操作执行两次。

## 推荐用法

无论执行成功还是失败，都应结束事务：

```python
session.begin_transaction()
try:
    session.execute("CREATE (:Person {name: 'Alice'})", access_mode="insert")
    session.commit()
except Exception:
    session.rollback()
    raise
```

显式事务应尽量保持简短。如果多条语句不需要一起提交，请使用自动提交。
