NeuG v0.1.3：图计算走进图数据库的时代

NeuG v0.1.3 通过 GDS 扩展带来 9 种原生图算法，并新增 COPY TEMP，支持临时加载外部数据进行分析。

NeuG v0.1.3 正式发布。本次版本的主题是：让图数据库拥有原生图计算能力。 GDS 扩展带来 9 种图算法；COPY TEMP 则让你可以加载外部数据进行临时分析，而不会污染生产数据库。

下面我们来谈谈为什么要构建这些能力，以及本次版本究竟发布了什么。

NeuG 一直缺少的能力：图计算

图数据库的核心能力是图存储，即用节点和边表示实体及其关系。借助 Cypher 的 MATCH 语句，你可以执行模式匹配查询：查找某个节点的邻居、匹配一条路径，或根据条件筛选子图。

但有一类问题是 Cypher 查询难以高效解决的：

  • 这张图中有多少个社区？哪些节点属于同一群组？
  • 哪个节点是最具影响力的枢纽？
  • 从节点 A 到其他所有节点的最短路径分别是什么？
  • 每个节点的局部聚类系数是多少？

这些是图算法问题，而不是图查询问题。二者的区别在于：图查询表达的是“我知道要找什么模式，请把它找出来”；图算法表达的是“请计算整张图的某种结构属性”。

此前 NeuG 不支持图算法，因此你必须导出数据，将其交给 NetworkX 等图分析库，计算结果后再导回。数据搬运、格式转换、环境配置——这些都是常见的工程开销。

v0.1.3 的 GDS 扩展将图算法直接带进图数据库。 无需导出数据，也无需维护第二套环境，只要执行 CALL 即可。

GDS：9 种算法，一套 API

算法概览

GDS 扩展覆盖三类最常用的图算法：

类别算法解决的问题
遍历与中心性WCC、BFS、SSSP、PageRank从 A 可以到达哪些节点？最短路径是什么？有多少个连通分量？哪个节点影响力最大？
社区发现Louvain、Leiden、CDLP有多少个社区？哪些节点属于同一群组？
结构分析LCC、K-Core图的连接程度如何？局部结构密度如何？

统一调用方式

所有算法都遵循同一种模式：先投影子图，再调用算法。

-- 1. 投影子图（定义参与计算的节点和边）
CALL project_graph(
    'social',
    ['person'],
    {'[person, knows, person]': ''}
);
 
-- 2. 调用算法
CALL page_rank('social', {max_iterations: 20})
RETURN node.fName, rank
ORDER BY rank DESC;
 
-- 3. 清理
CALL drop_projected_graph('social');

project_graph 用于定义计算范围，即哪些节点标签和边类型参与计算。完成投影后，所有算法都通过统一的 CALL algo_name('graph_name', {options}) 接口调用。返回值可以继续使用 ORDER BY、WHERE 和 RETURN 等标准 Cypher 子句处理。

BFS 和 SSSP 还支持返回完整路径：

CALL bfs('social', {source: '0'})
YIELD node, distance, path
RETURN node.fName, distance, nodes(path) AS path_nodes;

path 列是标准的 Cypher PATH 类型，支持 nodes(path)、relationships(path) 和 length(path)。

性能：LDBC Graphalytics 基准测试

我们在图分析领域公认的标准 LDBC Graphalytics 基准上评估了 GDS。测试覆盖 5 个数据集，边数从 10 亿到 18 亿不等，包括合成 R-MAT 图（graph500-26）、带权社交图（datagen-9 系列）以及真实社交图（com-friendster，18 亿条边）。我们将其与 SuiteSparse:GraphBLAS、GeminiGraph 和 ladybug 进行了对比（ladybug 仅实现 PR 和 WCC，且存在显著性能差距）。所有测试均在一台 32 核/64 线程、495GB RAM 的机器上运行，所有系统均使用 -O3 编译。

部分结果如下：

算法数据集NeuGGraphBLASGeminiGraph
CDLPdatagen-9_2-zf19s316s—
LCCdatagen-9_021.8s65.1s—
SSSPdatagen-9_01.14s6.47s1.24s
BFScom-friendster0.84s1.58s0.99s
WCCcom-friendster0.95s1.14s8.47s

各算法分析：

  • CDLP（标签传播）：在所有数据集上速度最快——在 datagen-9_2-zf 上比 GraphBLAS 快 16 倍（GeminiGraph 未实现该算法）
  • LCC（局部聚类系数）：在所有数据集上速度最快——在 datagen-9_0 上比 GraphBLAS 快 3 倍（GeminiGraph 未实现该算法）
  • SSSP（单源最短路径）：在三个带权数据集上均为最快——在 datagen-9_0 上比 GraphBLAS 快 6 倍，也略快于 GeminiGraph
  • BFS（广度优先搜索）/ WCC（弱连通分量）：在多数数据集上领先或与最佳结果持平
  • PageRank：与 GraphBLAS 接近；GeminiGraph 在部分数据集上略快

完整基准测试文档：GitHub 。

完整的算法列表、参数和用法请参阅 GDS 扩展文档。

临时图：加载外部数据、执行计算、不留污染

GDS 解决了“如何计算”的问题，但还有一个实际问题：数据从哪里来？

假设你想使用 GDS 分析一批外部数据——可能是从其他系统导出的关系数据、增量变更文件，或临时拼装的测试数据集。由于这只是一次性分析，你不希望在生产数据库中创建表；但要运行 GDS，又必须让这些数据以图的形式存在于数据库中。

v0.1.3 的 COPY TEMP 正是为此而生：

-- 加载临时节点表（来自 CSV）
COPY TEMP temp_user FROM 'users.csv' (header=true, primary_key='id');
 
-- 加载临时边表（指定起点和终点表）
COPY TEMP temp_knows FROM 'edges.csv' (header=true, from='temp_user', to='temp_user');

临时表有三个关键特性：

  1. 生命周期与 Connection 绑定——关闭连接后，所有临时表都会自动清理，无需手动执行 DROP TABLE。
  2. 不写入 Checkpoint——重启后即消失，绝不会污染持久化数据。
  3. 可与持久化数据混合使用——标准 Cypher JOIN 可以跨临时表与持久化表执行。

支持 CSV / JSON / JSONL / Parquet 格式。结合 v0.1.2 的 httpfs 扩展，还可以直接从 OSS / S3 / HTTPS 远程路径加载。COPY TEMP 的详细信息请参阅数据导入文档。

实战：从代码变更中发现新概念

GDS 与 COPY TEMP 结合，可以解决一个真实问题：代码变更会如何影响知识图谱？

场景

以 NeuG 代码库为例。我们将 NeuG 代码库（截至 v0.1.2）解析为一张图：函数作为节点，函数调用关系作为边（实际的代码图 Schema 会更复杂，还会包含 import 等关系，此处仅作简化演示）。知识图谱叠加在同一张图上：每个函数都标记了它所属的概念，例如 execute_query() 属于“查询执行”概念。

NeuG 发布 v0.1.3 后，代码仓库中出现了新的变更（新功能模块、文档更新等）。我们想知道：这些代码变更会对知识图谱造成什么影响？是否需要增加新概念？

解决方法是：把 v0.1.3 的新代码解析为增量图（新函数节点 + 调用边），通过 COPY TEMP 临时加载，再用 GDS 分析其结构：

  • 哪些新代码模块最具影响力？
  • 新代码变更形成了多少个社区？每个社区是否暗示着一个新概念？

这是一项预分析：在决定是否应用变更之前，我们不希望污染生产知识库，因此 COPY TEMP 非常适合。

代码图与增量数据

生产数据库中已经存在当前的代码图：从 v0.1.2 代码库解析得到的函数节点和调用边，以及概念节点和“函数 → 概念”的归属关系。

v0.1.3 的新代码被解析为增量 CSV 文件：新函数节点（例如 project_graph、page_rank、leiden、bfs 等）及其调用边。我们使用 COPY TEMP 临时加载增量数据，再用 GDS 分析它的社区结构。如果新函数自然聚集成若干社区，就说明知识图谱可能需要增加新概念。

分析流程

from neug import Database
import tempfile, os
 
# 1. 创建数据库（包含持久化代码图，用于模拟生产环境）
db = Database(db_path=tempfile.mkdtemp(), mode="w")
conn = db.connect()
 
# [持久化代码图已存在：函数节点 + 调用边 + 概念归属关系]
 
# 2. 加载 GDS 扩展
conn.execute("install gds")
conn.execute("load gds")
 
# 3. 从 v0.1.3 代码解析出的新函数和调用边（CSV 由代码分析工具提供）
nodes_csv = os.path.join(tempfile.gettempdir(), "delta_funcs.csv")
edges_csv = os.path.join(tempfile.gettempdir(), "delta_calls.csv")
# ……写入 CSV 文件……
 
# 4. COPY TEMP：将增量代码加载为临时图（不污染持久化数据）
#    注意：实践中，增量调用边也可能连接到持久化 func 节点
#    （新代码调用已有函数，或反之）；这里简化为 delta_func 内部调用
conn.execute("COPY TEMP delta_func FROM '{}' (header=true, primary_key='id')".format(nodes_csv))
conn.execute("COPY TEMP delta_call FROM '{}' (header=true, from='delta_func', to='delta_func')".format(edges_csv))
 
# 5. 投影增量代码图
conn.execute("""
    CALL project_graph(
        'delta_graph',
        ['delta_func'],
        {'[delta_func, delta_call, delta_func]': ''}
    )
""")
 
# 6. PageRank：哪些新代码模块最具影响力？
result = conn.execute("""
    CALL page_rank('delta_graph', {max_iterations: 20})
    RETURN node.name, rank
    ORDER BY rank DESC
""")
# （示例结果）
# project_graph        -> 排名最高（被 page_rank、leiden、wcc、bfs 调用，是增量图的枢纽）
# ……
# NodeDatabase::Init   -> 较低（仅被 InitAll 调用）
 
# 7. Leiden：新代码变更形成了多少个社区？
#    此处在增量图上运行社区发现；实践中也可在持久化图 + 增量图的组合图上运行
#    Leiden，并与原有社区比较，以发现新出现的社区 → 提示新概念
result = conn.execute("""
    CALL leiden('delta_graph', {concurrency: 1})
    RETURN node.name, community
    ORDER BY community
""")
# （示例结果，实际社区划分可能随算法参数变化）
# A 组：project_graph、page_rank、leiden、wcc、bfs、parse_subgraph_entries
# B 组：InitAll、NodeDatabase::Init
# -> 两个主要群组：图分析函数（6 个节点）-> 可能对应新概念“GDS Extension”
#    Node.js Binding 函数（2 个节点）-> 可能对应新概念“Node.js Binding”
 
# 8. 清理
conn.execute("CALL drop_projected_graph('delta_graph')")
conn.close()
# -> 临时表自动清理
 
# 9. 验证：重新打开连接，持久化代码图保持完好
conn2 = db.connect()
result = conn2.execute("MATCH (n:func) RETURN count(n)")
 
conn2.close()
db.close()

分析结论

PageRank 显示：project_graph 是新代码中最具影响力的函数——它被 page_rank、leiden 等算法函数调用，是新代码的核心枢纽。

Leiden 显示：新代码形成了多个社区——GDS 函数（project_graph、page_rank、leiden 等，共 6 个节点）紧密耦合，说明 v0.1.3 的代码变更可能需要在知识图谱中新增“GDS Extension”概念；Node.js Binding 函数（InitAll、NodeDatabase::Init，共 2 个节点）相对独立，可以作为单独的概念处理。

这就是“从代码图中发现新概念”的核心思路：通过 COPY TEMP 临时加载代码更新，使用 GDS 分析其社区结构，而新出现的社区则提示知识图谱需要增加新概念。整个分析过程中，生产数据库的数据从未被修改。连接关闭后，COPY TEMP 创建的临时表会自动清理，持久化数据保持完好。

其他值得关注的改进

v0.1.3 还有几项改进：

  • Node.js Binding（#424 ）：基于 N-API 的原生 C++ 插件，提供 Database、Connection、QueryResult 高层 API，支持嵌入式图数据库与 Cypher 查询。安装命令：npm install @graphscope-neug/neug。
  • COW 快照隔离（#370 ）：UpdateTransaction 改用 Copy-on-Write 快照隔离，提高读写并发的安全性。
  • 统一类型系统（#525 ）：统一编译器 LogicalType 与引擎 DataType，减少类型转换开销。
  • 数据库目录管理重构（#148 ）：引入 Module、Checkpoint 和 CheckpointManager，改进数据库目录管理。
  • macOS ARM64 CI（#576 ）：新增专用的 macOS ARM64 测试工作流，保障 Apple Silicon 平台质量。
  • 关键缺陷修复：修复非标准列名导致 Parquet 加载 0 行的问题（#455 ），以及 macOS ARM64 每夜构建失败的问题（#515 、#517 ）。
