你和你的 LLM 无法一次审查数千个 PR，但图数据库可以

CodeGraph 与 NeuG 如何通过图驱动的风险评分、冲突检测和影响范围分析，将大规模 PR 审查从凭直觉转变为数据驱动。

146 个待处理 PR，其中 83 个聚集成了冲突组，有些甚至在 5 个不同分支中修改同一个函数。这并非假设场景，而是 2026 年 5 月某个普通星期二，qwen-code  仓库的真实状态。况且 qwen-code 还不算极端，OpenClaw 和 Hermes 等项目经常有数千个待处理 PR。

人工审查如此多的 PR 并不现实，而要发现它们之间隐藏的冲突几乎不可能，即使对 LLM 也是如此。本文将通过对 qwen-code 146 个待处理 PR 的真实分析，介绍 CodeGraph  如何把 PR 管理从“凭直觉”转变为“数据驱动”。CodeGraph 是一款代码分析工具，由嵌入式图数据库 NeuG  提供支持。

PR 审查瓶颈：为什么你和你的 LLM 都跟不上

设想一下：你是一个热门开源项目的维护者。早晨打开 GitHub，发现有 146 个 PR 等待审查。它们来自世界各地的贡献者：有的涉及核心配置，有的重构工具调用流水线，还有的只是修正文档中的拼写错误。更糟的是，其中几个 PR 修改了同一个函数，合并任何一个都可能破坏其他 PR。

传统人工审查有三个根本限制：

  • 规模限制：一次只能审查一个 PR，而任何人都不可能在一个上午处理完 146 个。
  • 关联盲区：没有人能在脑中持续追踪哪些 PR 修改了同一个函数，更不用说判断 PR A 和 PR B 是否都改动了同一套底层逻辑。
  • 凭感觉判断风险：“这看起来风险很高”并不是指标，因为它没有结构化的风险评估。

那么使用 LLM 呢？当前的 AI Code Review 方案会逐个把 PR diff 交给语言模型。这在规模较小时有效，但面对 146 个 PR，token 消耗会急剧膨胀。更关键的是，LLM 天生无法执行跨 PR 关联分析。每次调用只能看到单个 PR 的 diff，无法回答“还有哪些 PR 修改了与当前 PR 相同的函数？”这类全局问题。

CodeGraph 选择了不同的路径：通过图数据库进行结构分析，而不只是通过 LLM 理解文本。它把代码仓库索引成可查询的知识图谱，其中包含函数、调用链、类、文件和 PR，再以图查询的方式执行风险评分、冲突检测和影响范围计算。整个过程不消耗 token，却能回答人类和 LLM 都难以处理的全局关联问题。

CodeGraph 如何工作：从代码仓库到知识图谱

CodeGraph 构建于 NeuG 之上。NeuG 是一款开源嵌入式图数据库，支持与 Neo4j 兼容的 Cypher。NeuG 在进程内运行，无须部署服务器，既具备图查询的表达能力，又像本地数据库文件一样简单易用。

pr-review 工作流分为两个阶段：

# 阶段 1：分析 + 检测 + 持久化
codegraph pr-review prepare --db .codegraph --repo owner/repo
 
# 阶段 2：在 GitHub 上添加标签 + 评论
codegraph pr-review label --db .codegraph --repo owner/repo

在 prepare 阶段，CodeGraph 会获取所有待处理 PR，以函数粒度解析其 diff，并把结果写入图数据库，包括 PR 节点、Function 节点以及连接两者的 CHANGES 边。这些数据与已有的代码结构图共存，后者包含调用关系、文件归属和类层次结构，因此可以在统一模型中执行跨 PR、跨代码查询。

关键在于：一旦把 PR 建模为图节点，并将其连接到所修改的函数，“哪些 PR 存在冲突？”这样的问题就会变成简单的图遍历，无须逐对比较 diff。

QwenLM/qwen-code 的 146 个 PR：真实案例分析

我们在活跃的开源 AI 编码助手项目 QwenLM/qwen-code 上运行了 CodeGraph。分析时，该项目位于 2026-05-13 的提交 870bdf2a，共有 146 个待处理 PR。以下是 CodeGraph 的发现。

单个 PR 风险评分

CodeGraph 会对每个 PR 执行结构化风险评分。它并非简单统计 diff 行数，而是解析每个 hunk，识别修改、新增和删除的函数，再根据以下因素计算综合得分：

  • 接口变更：修改抽象类或接口定义，例如 Tool 基类的方法签名
  • 配置文件：涉及配置或 schema 文件，例如 settings.json、tsconfig.json
  • 跨模块：横跨多个模块，例如同时修改 cli/ 和 core/
  • 死代码：引入未被调用的函数
  • 影响范围：被修改函数的上下游调用范围（fan_in × fan_out）

每个 PR 都会获得一个风险等级：LOW / MEDIUM / HIGH / CRITICAL。

风险分布： 🔴 CRITICAL：10 · 🟠 HIGH：32 · 🟡 MEDIUM：63 · 🟢 LOW：40

跨 PR 冲突检测

这是 CodeGraph 最具特色的能力。当两个 PR 修改同一个函数时，它们会通过图中的 Function 节点关联起来。只需一条 Cypher 查询即可找出所有这类冲突：

MATCH (pr1:PR)-[c1:CHANGES]->(f:Function)<-[c2:CHANGES]-(pr2:PR)
WHERE pr1.id < pr2.id
  AND c1.info IN ['hunk', 'deleted']
  AND c2.info IN ['hunk', 'deleted']
RETURN pr1.id, pr2.id, f.name, f.file_path;

在这些成对冲突之上，并查集（Disjoint Set Union，DSU）算法会计算连通分量。每个分量都成为一个“冲突组”，其中的 PR 直接或间接共享修改目标。

结果：146 个 PR 中有 83 个被归入 4 个冲突组。

三种分类

CodeGraph 自动把全部 146 个 PR 分为三类，并给出可执行的处理方式：

类别数量操作
自动合并候选31LOW 风险且无冲突，可快速合并
独立审查32存在一定风险但无跨 PR 冲突，可以任意顺序审查
冲突组83（4 组）修改了相同函数，需要协调审查

自动合并候选（31 个 PR）是最容易处理的部分，包括发布自动化、纯文档修改和配置版本更新。它们可以进入“轻量审查”通道，不会阻塞其他工作：

  • #4100 chore(release): v0.15.11 — 发布自动化，零风险
  • #4051 docs: --json-schema structured output user and design docs — 纯文档修改

独立审查（32 个 PR）确实存在风险，但可以单独审查：

  • #439 feat(tools): Include the new content after edits — CRITICAL，影响范围 = 100。它同时涉及配置 schema 和工具流水线，但不与任何其他 PR 冲突。

冲突组 1（77 个 PR）才是真正的主战场：这是仓库中最复杂的冲突网络，所有 PR 都通过对相同函数的修改彼此连接：

  • #3982 refactor(core): collapse three task registries into one — CRITICAL，影响范围 = 132，修改了 5 个文件中的接口
  • #4088 feat(cli): add session-scoped /goal command — CRITICAL，影响范围 = 140，涉及 hooks 执行流水线

根本原因在于，qwen-code 是一个同时覆盖 CLI、Core 和 VSCode 扩展的多端项目。loadCliConfig、LoadedSettings.loadSettings 和 sendMessageStream 等函数天然是汇聚点；不同贡献者从各自的功能分支修改这些枢纽函数，最终必然会被聚集到同一个连通分量中。

将结果推送到 GitHub

CodeGraph 不止完成分析，还会通过 codegraph pr-review label 把结果直接推送到 GitHub：

  • 为每个 PR 添加分类标签（auto-merge-candidate / independent-review / conflicting-group-N），可直接在 PR 列表中查看。
  • 在冲突组 PR 下发表评论，列出具体冲突的 PR 编号和共享函数名。贡献者无需维护者手动介入，就能看到“你的修改可能在函数 loadCliConfig 上与 #3455 和 #2220 冲突”。

你可以使用 --dry-run 模式在执行前预览：

codegraph pr-review label --db .codegraph --dry-run

为什么用图，而不是 LLM？

一个自然的问题是：为什么不把全部 146 个 diff 直接交给 LLM？

答案在于结构。LLM 按顺序处理文本，每次调用只能孤立地看到一个 PR 的 diff。要发现 #3982 和 #4088 都修改了 loadCliConfig，就必须把全部 146 个 diff 放进同一个上下文（以当前上下文长度无法实现），或者构建显式的外部索引，而后者正是图数据库所做的事。

CodeGraph 颠倒了处理模式：结构分析优先，LLM 其次。风险评分、冲突检测和影响范围都是纯图查询，不消耗 token。LLM 预算因此可以留给真正需要深度语义推理的 PR，例如：“这次重构安全吗？新的错误处理是否覆盖了所有边界情况？”图分析告诉你应该去哪里看，LLM 则帮助你判断在那里发现的内容。

它不是 AI Code Review 的替代品，而是让 AI Code Review 能够在大规模场景下落地的上游基础设施。

要点总结

对于活跃项目的维护者： 如果 PR 队列经常超出你的脑力建模范围，基于图的冲突检测可以在审查开始前提供一张“战场地图”。仅识别出 21% 的自动合并候选，就足以证明这套方案值得部署。

对于使用 AI Code Review 工具的团队： CodeGraph 是一层前置过滤器，它会告诉你应该把哪些 PR 交给 LLM 审查，以及应按什么顺序处理。不要在可以安全合并的 PR 上浪费 token，也不要在 PR 之间存在隐藏依赖时孤立审查。

对于开发者工具的构建者： “把代码建模为图，用 Cypher 查询关系”这一模式不只适用于 PR 审查，还能广泛用于死代码检测、影响分析、架构约束、Bug 根因追踪等场景。CodeGraph skill 文档 介绍了全部能力。

在你自己的仓库中试用

# 安装
pip install codegraph-ai
 
# 为仓库建立索引
codegraph init --repo . --lang auto --commits 500
 
# 执行 PR 审查
codegraph pr-review prepare --db .codegraph --repo owner/repo
codegraph pr-review label --db .codegraph --repo owner/repo --dry-run

完整分析工具集包括调用图、死代码、架构报告、模块耦合和 Bug 根因追踪，详见 CodeGraph skill 参考文档 。底层图引擎 NeuG  已开源，并专为嵌入开发者工具而设计。
