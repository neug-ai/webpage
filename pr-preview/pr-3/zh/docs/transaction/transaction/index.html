事务管理

本文档描述了 NeuG 的事务管理系统，该系统在不同部署模式下具有不同的运行机制。NeuG 支持两种主要模式：适用于分析型处理（AP）的 嵌入式模式（Embedded mode） 和适用于事务型处理（TP）的 服务模式（Service mode）。

设计理念

NeuG 的事务模型基于对图工作负载特征的深入理解，体现了相应的权衡取舍：

  • 图原生工作负载 以读操作为主，并频繁执行插入操作，而更新和模式变更则相对少见；
  • 分析型工作负载 更注重单次查询的吞吐量，而非复杂的强一致性保证；
  • 事务型工作负载 则要求在并发读/插入场景下具备高性能，同时提供强隔离性。

NeuG 并未采用一种高复杂度、试图“一统天下”的通用事务系统，而是针对不同工作负载提供相适应的事务保证，在简洁性、性能与正确性之间取得平衡。

事务模型

v0.2 版本之前

NeuG 仅暴露了一种隐式的、自动提交的事务模型。它没有提供用户可见的显式事务原语：每次调用 execute() 或 Query() 都是一个语句级事务。

 
# 每次 execute() 都是一个独立的、自动提交的事务。
conn.execute("CREATE (p:Person {name: 'Alice'})")  # 事务 1
conn.execute("CREATE (p:Person {name: 'Bob'})")    # 事务 2

自 v0.2 版本起

自动提交（Auto-commit）在所有受支持的接口中仍为默认行为。此外，以下客户端支持以编程方式显式地管理事务：

显式事务跨越多个查询：首先开启一个事务，然后在该事务内执行查询，最后提交或回滚该事务。只读事务会固定一个读取视图，并拒绝任何写入操作；而读写事务则拥有一个私有的写时复制（COW）视图，可读取自身已成功执行的写入操作，并且仅当提交成功后才将变更发布出去。

两种模式均不支持保存点（Savepoints）和部分回滚（partial rollback）。事务生命周期限制也有所不同：嵌入式 AP 事务永不超时，因此应用程序必须主动完成它；而 TP 服务端事务可能具有服务端配置的绝对生命周期上限，并可由服务端主动终止。

在显式事务内部不支持

在事务处于活动状态时，两种模式均拒绝执行相同类别的语句：

被拒绝的语句具体示例
批量、文件及临时加载语句COPY … FROM、COPY … TO、COPY TEMP、LOAD FROM
管理类语句CHECKPOINT，以及扩展的 INSTALL / LOAD / UNINSTALL
可变状态的过程调用调用会改变状态的过程（例如 project_graph 或 drop_projected_graph）的 CALL；只读的 CALL 是允许的

其余所有操作均被允许，包括读取、插入、更新、删除，以及常规 DDL 操作，例如 CREATE NODE TABLE、ALTER、DROP 和索引创建。 被拒绝的语句行为与其他任何失败语句一致：它会使当前事务变为仅可回滚（rollback-only）状态。

失败与仅回滚状态

一条语句在抵达数据库后执行失败，将使其所属事务进入仅回滚（rollback-only）状态：该事务无法再提交，且必须在客户端发出下一条查询或启动下一个事务之前终止。属于此类失败的情形包括：

  • 语义分析、语法或编译错误
  • 执行失败
  • 在只读事务中尝试执行写操作
  • 任何被上表所拒绝的语句
  • 以查询形式提交的 Cypher BEGIN、COMMIT 或 ROLLBACK —— 这些语句不受支持；请改用客户端提供的事务控制方法

客户端绑定在语句抵达数据库之前所拒绝的错误，不会影响当前事务。例如，Python 会以 ValueError 拒绝无效的 access_mode，而事务仍可正常使用。

嵌套的 begin 调用以及非法的程序化控制调用，会报告事务状态错误，但不会改变原本处于活跃状态的事务。

仅回滚事务的终止方式取决于所使用的模式；详见下方两个小节。

嵌入式 AP 模式中的显式事务

在嵌入式模式下，一个显式事务由其所属的 Connection 对象拥有。

auto status = conn->BeginTransaction(neug::TransactionMode::kReadWrite);
if (!status.ok()) {
  // 处理事务开始失败的错误。
}
 
auto created = conn->Query("CREATE (:Person {name: 'Alice'})", "insert");
auto visible = conn->Query("MATCH (p:Person) RETURN p.name", "read");
 
status = conn->Commit();  // 将所有成功的写操作作为一个整体提交。
conn.beginTransaction();
 
const created = conn.execute("CREATE (:Person {name: 'Alice'})", 'insert');
const visible = conn.execute('MATCH (p:Person) RETURN p.name', 'read');
 
conn.commit(); // 将所有成功的写操作作为一个整体提交。
conn.begin_transaction()
created = conn.execute("CREATE (:Person {name: 'Alice'})", "insert")
visible = conn.execute("MATCH (p:Person) RETURN p.name")
conn.commit()

当客户端未指定事务模式时，读写（READ_WRITE）是默认模式；每个客户端还提供其 begin 调用的只读（READ_ONLY）变体。具体函数签名请参阅 Python、 Node.js 和 C++ 的连接 API 参考文档。

并发性：一个读写事务在其整个生命周期内独占 AP 访问权限：所有其他 AP 操作均需等待该事务提交、回滚或其关联连接关闭后才能执行。嵌入式 READ_WRITE 模式还限制同一时刻仅允许存在一个公开的 Connection。

生命周期：事务无超时机制。它将持续保持打开状态，直至应用程序主动终止；在其打开期间，其他任何 AP 工作均无法进行——因此请务必及时结束事务。

终止仅可回滚的事务：应显式调用回滚（rollback），或直接关闭连接。在完成上述任一操作之前，该连接仍将报告存在一个活跃事务。

TP 服务模式下的显式事务

在服务模式下，一个显式事务由其所属的 Session 拥有，且一个 Session 在任意时刻最多只能拥有一个事务。

from neug import Session
 
session = Session.open("http://localhost:10000", num_threads=1)
session.begin_transaction()
session.execute("CREATE (:Person {name: 'Alice'})", "insert")
assert list(session.execute("MATCH (p:Person) RETURN p.name")) == [["Alice"]]
session.commit()
session.close()
import com.alibaba.neug.driver.Driver;
import com.alibaba.neug.driver.GraphDatabase;
import com.alibaba.neug.driver.Session;
import com.alibaba.neug.driver.Transaction;
 
try (Driver driver = GraphDatabase.driver("http://localhost:10000");
        Session session = driver.session();
        Transaction txn = session.beginTransaction()) {
    txn.run("CREATE (:Person {name: 'Alice'})").close();
    txn.run("MATCH (p:Person) RETURN p.name").close();
    txn.commit();
}

有关服务模式下事务控制的详细信息，请参阅 Python Session 参考文档 和 Java 事务 API 文档。

会话的使用。 Python 将在活跃 Session 上发出的查询自动路由至其关联的事务中。而在 Java 中，所有事务性语句必须通过 Transaction.run(...) 执行；直接调用 Session.run(...) 将被拒绝，直至当前事务结束。两种客户端均限制每个 Session 最多持有一个显式事务；关闭 Session 时，若其中存在未结束的事务，则会尝试将其回滚。切勿通过单个 Session 并发发出请求——应为每个客户端工作线程分配独立的 Session。模式查询（Schema lookups）始终返回服务端已提交的全局模式，而绝不会返回事务私有的模式。

并发性。 读写事务持有 TP 更新租约（update lease）。在其持有期间，其他读写事务无法启动，普通插入与更新操作需等待其完成；而读操作仍可并发执行。一次成功的提交将追加并发布一条 WAL 提交记录。

生命周期。 当事务的绝对生存期到期或服务关闭时，服务端会自动回滚并清除该事务。过期状态采用惰性报告机制：下一次事务请求将返回 410 Gone 状态码，随后 Session 清除其本地句柄。在服务关闭或网络故障后，本地状态可能已过时，此时应关闭 Session。普通语句执行失败会使事务进入仅回滚（rollback-only）状态。

结束仅回滚事务。 调用 rollback()（Java 中为 Transaction.rollback()）。若 Python 中的事务已过期，该调用在收到 410 Gone 响应时将抛出 RuntimeError，但仍会清除本地句柄。在 Java 中，若某条语句被 Transaction.run(...) 拒绝，则事务即进入仅回滚状态，此后仅允许调用 rollback()。若 Java 在提交或回滚过程中遭遇网络故障，则最终结果未知；驱动程序不会重试，且拥有该事务的 Session 必须被关闭并替换。

被遗弃的事务。 一个从未被显式结束的读写事务将持续持有更新租约，从而阻塞普通 TP 写入操作，直至服务端主动释放该租约。因此，务必确保在成功路径和失败路径上均显式结束事务。

ACID 特性

嵌入模式（面向分析处理，AP-oriented）

嵌入模式专为分析型工作负载设计，其设计重点在于简洁性和单次查询性能，而非复杂的事务保障。

原子性（Atomicity）

v0.2 版本之前： 大型分析处理（AP）写操作未完全保证语句级原子性。在大型写操作（例如 COPY）执行过程中若发生失败，可能导致部分数据残留在内存中。应用程序通常将检查点（checkpoint）用作此类操作的恢复点；有关检查点生命周期及 checkpoint_on_close 行为，请参阅 Checkpoints。

自 v0.2 版本起： 普通 AP 写操作使用私有的写时复制（COW）图，并仅在 WAL 提交成功后才将其发布。持久化的直接批量操作同样使用该私有图，并在成功时发布一个检查点；临时批量对象则仅驻留在内存中。显式的读写事务会将其所支持的普通写操作累积至一个私有图中，并仅在调用 Commit() 时统一发布。

当前 WAL 格式已足以支持常规重放（replay），但其最终的帧格式（framing）、损坏处理（corruption handling）以及“提交状态未知”（commit-unknown）情形下的恢复规则仍在持续加固中。对于在批量加载后需要具备持久化物化检查点（durable materialized checkpoint）的应用程序，应采用 Checkpoints 中所述的检查点生命周期机制。

一致性

模式约束和引用完整性在语句级别上强制执行。无效的操作（例如创建重复的主键或违反边约束）将被拒绝。

隔离性

所有写操作均采用悲观独占锁（Pessimistic exclusive locking）。任何写语句（包括插入、更新、删除或模式修改）都会获取一个独占锁，阻塞所有其他操作，直至该写操作完成。

操作类型并发行为
读 + 读允许并发执行
写 + 读 / 写互斥

这种简单的锁机制足以满足单用户分析型工作负载的需求，并避免了细粒度并发控制的复杂性。

持久性

v0.2 版本之前： AP 的变更仅在显式执行 CHECKPOINT 语句，或以 checkpoint_on_close=True 参数关闭数据库时才会被持久化。

自 v0.2 版本起： 普通的 AP 写入操作（包括一次成功的显式读-写提交）会将逻辑重做日志追加至 WAL，并在正常重启时重放。持久化的直接批量操作则通过发布其检查点（checkpoint）来实现持久性。显式的 CHECKPOINT 语句，或以 checkpoint_on_close=True 参数关闭数据库，将创建一个物化的检查点并管理 WAL 的轮转。

对于内存数据库，由于数据仅存在于易失性内存中，因此不涉及持久性。有关使用方式及故障行为，请参阅 检查点（Checkpoints）。

服务模式

服务模式专为高吞吐量事务型工作负载及并发客户端访问而设计。其并发模型针对图原生访问模式进行了优化，适用于以读取和插入操作为主的场景。

原子性

每条语句均作为“全有或全无”的操作执行。失败的语句会自动回滚，且其他事务无法看到任何部分状态变更。

一致性

强制执行模式约束和引用完整性。所有并发操作均观察到数据库的一致视图。

隔离性

NeuG 采用多版本并发控制（MVCC） 提供可串行化隔离，并针对不同操作类型定义了特定的并发规则：

操作类型并发行为
读取（Read）读取一个一致的快照；在活跃的插入/更新期间仍可继续执行。
插入（Insert）可与读取及其他插入操作并发执行；若当前有更新正在进行，则需等待。
更新（Update）一次仅允许一个更新操作执行；读取操作可在一致快照上持续进行；插入及其他更新操作需等待当前更新完成。
模式变更（Schema，DDL）并发行为与更新操作相同。
检查点（Checkpoint）独占式维护操作；详见 Checkpoints。

注意：若读取请求在更新操作即将完成时到达，可能短暂等待，通常为毫秒级。

设计依据：该混合策略反映了图计算工作负载的实际特征：

  • 读取和插入 是大多数图应用（如社交网络、知识图谱、推荐系统）中最主要的操作；
  • 更新和模式变更 相对罕见，因此被串行化处理；而读取操作始终基于一致快照持续运行，仅在写入操作即将完成时短暂等待；
  • 检查点 属于数据库级别的维护操作；其并发行为详见 Checkpoints；
  • 若对所有写入类型均实现完整的 MVCC，将显著增加系统复杂度，但对典型的图工作负载而言收益甚微。
from neug import Session
 
# 并发会话
session1 = Session("http://localhost:10000/")
session2 = Session("http://localhost:10000/")
 
# 这些操作可以并发执行（读取 + 插入）
session1.execute("MATCH (p:Person) RETURN count(p)", access_mode="read")
session2.execute("CREATE (p:Person {name: 'Bob'})", access_mode="insert")
 
# 此更新与插入及其他更新串行执行。
# 更新运行期间，读取仍在一致快照上继续执行。
session1.execute("MATCH (p:Person) SET p.updated = true", access_mode="update")

持久性

所有修改均通过 预写式日志（WAL） 立即持久化：

  • 在执行完成前，变更已记录到 WAL 中
  • 崩溃恢复时会自动重放 WAL，以恢复一致状态
  • 持久性无需显式执行检查点；检查点仅用于 WAL 合并。参见 检查点

访问模式

执行查询时，您可以指定 access_mode 以控制事务行为并优化性能：

模式别名描述
readr只读操作（不包含修改的 MATCH 查询）
inserti仅插入操作（CREATE 新顶点/边）
updateu更新/删除操作（SET、DELETE、MERGE）
schemas模式修改操作（CREATE/DROP 节点/边表）

默认行为： 若未显式指定，则 NeuG 将自动推断合适的模式。在 Service 模式下，显式指定正确的访问模式可实现更优的并发性能优化。

访问模式能力说明： 访问模式是按操作类型区分的，而非严格的层级关系。在 Service 模式下，read 和 insert 属于窄范围模式，而 update 和 schema 则使用通用的串行化更新路径。若指定的模式不支持计划执行的操作，将返回错误。

下表仅适用于 Service 模式：

指定的模式实际执行的操作结果
readread✅ 成功
readinsert/update/schema/checkpoint❌ 错误
insertinsert✅ 成功
insertread/update/schema/checkpoint❌ 错误
updateread/insert/update/schema/checkpoint✅ 成功（走串行化更新路径）
schemaread/insert/update/schema✅ 成功（走串行化更新路径）

在 Embedded 模式下，除 read 外的其他模式主要影响查询锁的类型（共享锁 vs. 排他锁），而非采用不同的事务实现机制。显式指定 read 模式仍会拒绝写操作；此外，下方所述的特殊 CHECKPOINT 限制在两种部署模式下均适用。

CHECKPOINT 是一种特殊的管理语句。有关其支持的访问模式以及 EXPLAIN/PROFILE 行为，请参阅 Checkpoints。

 
# 最优实践：为获得最佳并发性能，将访问模式与操作相匹配
conn.execute("MATCH (n) RETURN n", access_mode="read")        # 仅读锁
conn.execute("CREATE (p:Person {name: 'Alice'})", access_mode="insert")  # 插入锁
 
# 可运行但非最优：读取查询的更新模式会进入更新路径
conn.execute("MATCH (n) RETURN n", access_mode="update")      # 可运行，但会降低写入并发性

数据持久化

嵌入模式：WAL 与检查点（Checkpoint）

自 v0.2 起，已提交的常规写入操作会被保存至 WAL（Write-Ahead Log），并在重启后自动恢复。 持久化的 COPY ... FROM 操作会在报告成功前创建一个检查点；而 COPY TEMP 则仅驻留在内存中，数据库关闭时其数据将丢失。 为保证数据持久性，手动执行检查点并非必需，但可减少恢复过程中需重放的 WAL 数据量。详情请参阅 检查点（Checkpoint）。

服务模式：基于 WAL（预写式日志）

变更通过预写式日志（Write-Ahead Logging，WAL）自动持久化：

from neug import Session
 
session = Session("http://localhost:10000/")
 
# 每条语句均立即具备持久性
session.execute("CREATE (p:Person {name: 'Alice'})")  # 通过 WAL 实现持久化
session.execute("CREATE (p:Person {name: 'Bob'})")    # 通过 WAL 实现持久化
 
session.close()

可选的检查点（checkpoint）可用于合并 WAL，但并非语句持久性的必要条件。参见 检查点。

错误恢复

嵌入模式

启动时，NeuG 会加载由 CURRENT 指定的检查点，并自动重放该检查点 base_ts 之后已提交的 WAL 记录。失败或未提交的私有写时复制（copy-on-write）更改永远不会发布。有关恢复行为和故障处理，请参阅检查点。

服务模式

使用 WAL 实现自动崩溃恢复：

  • 未提交的操作将自动回滚
  • 数据库在启动时恢复到最后的一致状态
  • 无需人工干预

最佳实践

嵌入模式

import neug
 
db = neug.Database("/path/to/database")
conn = db.connect()
 
# 1. 创建 schema；普通已提交写入操作由 WAL 提供支持
conn.execute("CREATE NODE TABLE Person(id INT64, name STRING, PRIMARY KEY(id))")
conn.execute("CREATE NODE TABLE Company(id INT64, name STRING, PRIMARY KEY(id))")
conn.execute("CREATE REL TABLE WORKS_AT(FROM Person TO Company)")
 
# 可选维护：物化状态并合并 WAL
conn.execute("CHECKPOINT")
 
# 2. 每个持久化的 COPY ... FROM 在成功执行时都会发布自己的检查点
conn.execute("COPY Person FROM 'employees_batch1.csv'")
conn.execute("COPY Person FROM 'employees_batch2.csv'")
conn.execute("COPY Company FROM 'companies.csv'")
conn.execute("COPY WORKS_AT FROM 'employment.csv'")
 
# 3. 运行分析查询（只读，高性能）
result = conn.execute("MATCH (p:Person)-[:WORKS_AT]->(c:Company) RETURN c.name, count(p)")
 
conn.close()
db.close()

服务模式（面向事务处理，TP-oriented）

from neug import Session
 
session = Session("http://localhost:10000/")
 
try:
    # 读取与插入操作可在不同会话间并发执行
    session.execute("CREATE (p:Person {name: 'Alice'})", access_mode="insert")
 
    # 读取操作不会阻塞插入操作
    result = session.execute("MATCH (p:Person) RETURN count(p)", access_mode="read")
 
    # 更新操作与插入操作及其他更新操作是串行化的。读取操作在一致的快照上继续执行，
    # 但在高并发场景下应尽量缩短更新操作的持续时间。
    session.execute(
        "MATCH (p:Person) WHERE p.name = 'Alice' SET p.verified = true",
        access_mode="update",
    )
 
    # 周期性检查点以合并 WAL（可选）
    session.execute("CHECKPOINT")
 
finally:
    session.close()
