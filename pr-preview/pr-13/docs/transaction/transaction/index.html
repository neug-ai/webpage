Transaction Management

NeuG provides ACID transactions in two deployment modes: Embedded mode, optimized for analytical processing (AP), and Service mode, optimized for transactional processing (TP). Auto-commit is the default everywhere: each query is its own transaction unless you group queries into an explicit transaction.

Deployment modes at a glance

Choose a mode based on your workload:

Embedded Mode (AP)Service Mode (TP)
Use caseAnalytics, ETL, batch processingInteractive applications, web services
AccessIn-process Connection (C++, Python, Node.js)Network Session (Python, Java)
Optimized forMaximum single-query performanceConcurrent read/insert throughput

The guarantees each mode provides are summarized under ACID guarantees.

ACID guarantees

Both modes provide the full set of ACID guarantees; the table summarizes them and the notes below highlight where the modes differ.

PropertyEmbedded Mode (AP)Service Mode (TP)
AtomicityAll-or-nothing; failed statements roll back automaticallySame as Embedded mode
ConsistencySchema constraints and referential integrity enforcedSame as Embedded mode
IsolationExclusive write locks; reads run concurrentlyMVCC: concurrent reads/inserts; serialized updates/DDL; exclusive checkpoints
DurabilityWAL for committed writes; checkpoints for persistent bulk loadAutomatic WAL persistence
  • Atomicity. Every statement is all-or-nothing. An Embedded read-write transaction accumulates its writes in a private copy-on-write view and publishes them only at commit. In Service mode, a failed statement is rolled back automatically, with no partial state visible to other transactions.
  • Consistency. Schema constraints and referential integrity are enforced at the statement level. Invalid operations, such as duplicate primary keys or violated edge constraints, are rejected.
  • Isolation. Embedded mode uses exclusive write locks; Service mode uses MVCC. See Isolation and concurrency.
  • Durability. Committed writes are persisted through a write-ahead log (WAL) and replayed on restart. See Durability and recovery and Checkpoints.

Run transactions

Auto-commit (default)

By default, every execute() / Query() call runs as its own transaction and commits automatically:

conn.execute("CREATE (p:Person {name: 'Alice'})")  # committed immediately
conn.execute("CREATE (p:Person {name: 'Bob'})")    # committed immediately

Explicit transactions

An explicit transaction groups several queries into one unit of work: begin it, run queries inside it, then commit or roll back. A read-only transaction pins one read view and rejects writes. A read-write transaction reads its own successful writes and publishes them only when the commit succeeds.

For per-client usage (C++, Python, Node.js, Java), the full rules and restrictions, and the failure/rollback behavior in each mode, see Explicit Transactions.

Isolation and concurrency

Embedded mode (AP)

Embedded mode uses pessimistic exclusive locking, which suits single-user analytical workloads. Reads run concurrently with each other, but any write statement (insert, update, delete, or schema change) takes an exclusive lock and blocks all other operations until it completes.

Service mode (TP)

Service mode uses Multi-Version Concurrency Control (MVCC) to provide serializable isolation, tuned for graph workloads where reads and inserts dominate:

OperationConcurrency
ReadReads a consistent snapshot; continues during active inserts/updates
InsertConcurrent with reads and other inserts; waits if an update is in progress
UpdateOne at a time; reads continue on a snapshot, inserts and other updates wait
Schema (DDL)Same as update
CheckpointExclusive maintenance; see Checkpoints

A read that arrives while an update is finishing may wait briefly, typically at millisecond scale.

from neug import Session
 
session1 = Session("http://localhost:10000/")
session2 = Session("http://localhost:10000/")
 
# Concurrent: reads do not block inserts
session1.execute("MATCH (p:Person) RETURN count(p)", access_mode="read")
session2.execute("CREATE (p:Person {name: 'Bob'})", access_mode="insert")
 
# Serialized with inserts and other updates; reads continue on a snapshot
session1.execute("MATCH (p:Person) SET p.updated = true", access_mode="update")

Access modes

Specify an access_mode to control transaction behavior and optimize concurrency:

ModeAliasesDescription
readrRead-only operations (MATCH without mutations)
insertiInsert-only operations (CREATE new vertices/edges)
updateuUpdate/delete operations (SET, DELETE, MERGE)
schemasSchema modifications (CREATE/DROP node/edge tables)

If not specified, NeuG infers the mode. Specifying the correct mode enables better concurrency optimization in Service mode. Using a mode that does not support the planned operation returns an error.

In Service mode, each access mode allows only certain operations:

Specified modeAllowed operations
readread
insertinsert
updateread, insert, update, schema, checkpoint
schemaread, insert, update, schema

read and insert are narrow modes limited to their own operation; update and schema use the general serialized update path and accept any operation (update also allows CHECKPOINT, while schema does not).

CHECKPOINT may use update only as an auto-commit request. It is rejected while an explicit transaction is active; end the transaction first. See Statements rejected inside an explicit transaction.

In Embedded mode, modes other than read mainly select shared versus exclusive query locking rather than distinct transaction implementations. Explicit read still rejects writes. CHECKPOINT is a special administrative statement in both modes; see Checkpoints for its accepted access modes and EXPLAIN/PROFILE behavior.

# Optimal: match the access mode to the operation
conn.execute("MATCH (n) RETURN n", access_mode="read")                  # read lock only
conn.execute("CREATE (p:Person {name: 'Alice'})", access_mode="insert")  # insert lock
 
# Works but suboptimal: update mode for a read enters the update path
conn.execute("MATCH (n) RETURN n", access_mode="update")

Durability and recovery

Committed writes are persisted automatically and recovered on restart; no manual checkpoint is required for durability. In-memory databases are not durable, as their data lives only in volatile memory.

Embedded mode. Committed ordinary writes append logical redo to the WAL and are replayed on a normal restart. A persistent COPY ... FROM publishes a checkpoint before reporting success; COPY TEMP stays in memory and is lost when the database closes. On startup, NeuG loads the checkpoint selected by CURRENT and replays committed WAL records after that checkpoint’s base_ts; failed or uncommitted copy-on-write changes are never published.

Service mode. Every statement is logged to the WAL before it completes. Crash recovery replays the WAL automatically: uncommitted operations are rolled back and the database restores to its last consistent state, with no manual intervention.

An optional checkpoint consolidates the WAL and reduces the amount replayed during recovery, and makes persistent bulk loads durable. See Checkpoints for the checkpoint lifecycle, concurrency, and failure behavior.

Best practices

The recommendations below distill the behavior described in this page. For the full rules on ending, rollback-only state, and per-mode concurrency of explicit transactions, see Explicit Transactions.

Both modes

  • Default to auto-commit. Rely on auto-commit unless several statements must succeed or fail together; open an explicit transaction only for that grouping.
  • Match the access mode to the operation. Pass read / insert / update / schema so NeuG picks the narrowest path. A read issued as update still works but enters the serialized update path; see Access modes.
  • End explicit transactions promptly, on both paths. Always commit or roll back in a try/finally (or the language’s equivalent). A read-write transaction that is left open holds a lease and stalls other work.
  • Never submit Cypher BEGIN / COMMIT / ROLLBACK as a query. Use the client’s transaction-control methods; the Cypher forms make the transaction rollback-only.

Embedded mode

  • Bulk-load with COPY ... FROM, not row-by-row inserts. Each persistent COPY publishes its own checkpoint on success and is far faster than many single-row writes; see Durability and recovery.
  • Keep read-write transactions short. A read-write transaction holds exclusive AP admission for its whole lifetime, so every other AP operation waits until it commits, rolls back, or its connection closes. There is no timeout — end it yourself.
  • Run analytical queries read-only. Reads run concurrently with each other and give the best single-query throughput; reserve writes for load and update phases.
  • Close the connection and database when done so pending state is flushed and locks are released.
import neug
 
db = neug.Database("/path/to/database")
conn = db.connect()
 
# Create schema; ordinary committed writes are WAL-backed
conn.execute("CREATE NODE TABLE Person(id INT64, name STRING, PRIMARY KEY(id))")
conn.execute("CREATE NODE TABLE Company(id INT64, name STRING, PRIMARY KEY(id))")
conn.execute("CREATE REL TABLE WORKS_AT(FROM Person TO Company)")
 
# Each persistent COPY ... FROM publishes its own checkpoint on success
conn.execute("COPY Person FROM 'employees_batch1.csv'")
conn.execute("COPY Person FROM 'employees_batch2.csv'")
conn.execute("COPY Company FROM 'companies.csv'")
conn.execute("COPY WORKS_AT FROM 'employment.csv'")
 
# Run analytical queries (read-only, high performance)
result = conn.execute("MATCH (p:Person)-[:WORKS_AT]->(c:Company) RETURN c.name, count(p)")
 
conn.close()
db.close()

Service mode

  • Use one Session per client worker. A Session owns at most one explicit transaction at a time; never issue concurrent requests through the same session.
  • Specify access_mode to keep reads and inserts concurrent. Reads run on a consistent snapshot and do not block inserts, so let them stay on the narrow read / insert paths; see Isolation and concurrency.
  • Keep updates short in high-concurrency scenarios. Updates and DDL are serialized and hold the TP update lease: while one runs, other inserts and updates wait (reads stay concurrent).
  • Always close the session, ideally in a finally. Closing tries to roll back any open transaction. An abandoned read-write transaction keeps the update lease and delays ordinary TP writes until the service releases it.
from neug import Session
 
session = Session("http://localhost:10000/")
 
try:
    # Reads and inserts can be concurrent across sessions
    session.execute("CREATE (p:Person {name: 'Alice'})", access_mode="insert")
 
    # Reads don't block inserts
    result = session.execute("MATCH (p:Person) RETURN count(p)", access_mode="read")
 
    # Updates are serialized; keep them short in high-concurrency scenarios
    session.execute(
        "MATCH (p:Person) WHERE p.name = 'Alice' SET p.verified = true",
        access_mode="update",
    )
finally:
    session.close()

Appendix

Design notes

NeuG’s transaction model reflects trade-offs based on graph workload characteristics: graph workloads are predominantly read-heavy with inserts, while updates and schema changes are relatively infrequent; analytical workloads prioritize single-query throughput; transactional workloads need concurrent read/insert performance with strong isolation. Rather than a one-size-fits-all system, NeuG provides workload-appropriate guarantees that balance simplicity, performance, and correctness.

Version history

Before v0.2, NeuG exposed only an implicit, auto-commit model with no explicit transaction primitives, and statement-level atomicity was not fully guaranteed for large AP writes; applications used checkpoints as recovery points around operations such as COPY. Since v0.2, ordinary writes use a private copy-on-write graph and a WAL, explicit transactions are available in the supported clients, and durability no longer depends on manual checkpoints.

Roadmap

  • More transparent recovery diagnostics for Embedded mode
  • Delta checkpointing for efficient incremental persistence
  • Reduced checkpoint blocking time for large datasets
  • Policy-driven periodic checkpointing
